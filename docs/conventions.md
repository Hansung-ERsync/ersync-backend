# ERSync 백엔드 개발 컨벤션

이 문서는 제품 설계안이 아닙니다. 안전한 협업을 위한 필수 가드레일과 기본
권장 방식만 정의합니다. 기능의 상세 설계는 담당 엔지니어가 AI와 현재 코드를
검토해 결정합니다.

## 1. 규칙 등급

| 등급 | 의미 |
|---|---|
| 필수 | 보안, 외부 계약, 데이터와 배포 안정성을 위해 반드시 준수 |
| 기본 권장 | 특별한 이유가 없으면 적용하되 다른 선택 가능 |
| 엔지니어 선택 | 기능 요구사항과 현재 코드에 맞춰 자율적으로 결정 |

기본 권장 방식과 다르게 구현하면 `implementation.md`에 이유와 영향을
기록합니다. 내부 설계 선택을 제품 정책으로 취급하지 않습니다.

## 2. 필수 규칙

### 2.1 보안과 데이터 접근

- 역할, 조직과 요청 소유권을 서버에서 검증합니다.
- 클라이언트가 보낸 사용자 ID나 조직 ID만으로 권한을 판단하지 않습니다.
- 슈퍼 관리자는 환자 임상정보와 위치정보를 조회할 수 없습니다.
- 실제 환자정보, 토큰, 비밀번호, 가입 코드, Secret과 정확한 GPS를 로그에 남기지 않습니다.
- 인증이 필요한 API는 프론트에서 버튼을 숨기는 것과 별개로 서버 권한을 검증합니다.

### 2.2 공통 오류 응답

모든 4xx와 5xx 응답은 다음 형식을 유지합니다.

```json
{
  "code": "COMMON_001",
  "message": "요청값 검증에 실패했습니다.",
  "fieldErrors": [],
  "traceId": "01JABC"
}
```

- 알려진 실패는 `CustomException(ErrorCode)`로 발생시킵니다.
- Controller나 Service에서 임의 오류 코드와 메시지를 만들지 않습니다.
- 내부 예외 메시지와 stack trace를 응답으로 반환하지 않습니다.
- 오류 코드의 현재 기준은
  [`ErrorCode.java`](../src/main/java/com/hansungteam/ersync/global/exception/ErrorCode.java)입니다.
- 새 오류는 고유 코드, 안전한 공개 메시지, HTTP 상태와 실패 경로 테스트를 함께 추가합니다.
- 기능에서 프론트가 처리할 오류는 해당 핸드오프 문서에 직접 기록합니다.

### 2.3 로그와 추적

- 모든 요청의 `X-Trace-Id`와 오류 응답 `traceId` 계약을 유지합니다.
- 로그에는 요청 본문과 응답 본문을 기록하지 않습니다.
- 동적 식별자가 포함된 경로보다 Spring route pattern을 우선 기록합니다.
- 예상 가능한 비즈니스·검증·인증 실패는 WARN, 예상하지 못한 시스템 실패는 ERROR로 기록합니다.
- 시스템 실패만 원인 stack trace를 남깁니다.

공통 로그 형식:

```text
event={} traceId={} code={} status={} method={} path={} message="{}" exception={}
```

### 2.4 DB와 Flyway

- 모든 스키마 변경은 새 Flyway migration으로 추가합니다.
- 파일명은 `V{버전}__{설명}.sql` 형식을 사용합니다.
- 이미 적용된 migration은 수정하지 않습니다.
- 운영 DB를 콘솔에서 임의로 변경하지 않습니다.
- 외부에 노출되는 식별자에 내부 순차 PK를 그대로 사용하지 않습니다.
- DB 제약조건과 애플리케이션 검증이 필요한 무결성 조건을 함께 검토합니다.

### 2.5 테스트

- 기능의 정상 흐름과 주요 실패 흐름을 검증합니다.
- 역할, 조직과 요청 소유권이 관련되면 권한 테스트를 추가합니다.
- 중복 명령이나 경합 가능성이 있으면 멱등성과 동시성 테스트를 검토합니다.
- JPA 매핑과 migration은 실제 MySQL 8.4 호환성을 확인합니다.
- H2는 빠른 검사 용도이며 MySQL 호환성의 최종 증명으로 사용하지 않습니다.
- DB 시각 응답은 저장 직전의 인메모리 `Instant`와 문자열로 정확히 비교하지 않습니다.
  `DATETIME(6)` 정밀도를 고려해 projection이나 재조회 값으로 응답을 검증하고,
  원본 시각과는 1마이크로초 이내인지 확인합니다.
- PR 전에 `./gradlew clean check`를 통과합니다.

### 2.6 외부 계약

- 기존 API를 호환되지 않게 바꾸기 전에 영향 범위와 전환 방법을 기록합니다.
- 요청·응답, 권한, 상태, 오류 또는 실시간 계약이 바뀌면 해당 프론트 핸드오프를 작성합니다.
- 핸드오프는 예정 설계가 아니라 구현과 테스트가 끝난 실제 계약만 포함합니다.

## 3. 기본 권장 방식

### 3.1 네이밍

| 대상 | 권장 | 예시 |
|---|---|---|
| 클래스·인터페이스 | PascalCase | `TransportService` |
| 메서드·변수 | camelCase | `createRequest` |
| 상수 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 패키지 | 소문자 | `transport` |
| Enum 값 | UPPER_SNAKE_CASE | `HOSPITAL_STAFF` |
| 요청 DTO | `Request` 접미사 | `CreateTransportRequest` |
| 응답 DTO | `Response` 접미사 | `TransportResponse` |

의미 없는 축약어와 `data`, `info`, `temp`처럼 범위가 불분명한 이름을 피합니다.

### 3.2 Java와 Javadoc

- 들여쓰기는 공백 4칸과 K&R 중괄호 스타일을 사용합니다.
- 사용하지 않는 import와 코드는 제거합니다.
- 불변 DTO는 Java record를 우선 검토합니다.
- 주석은 코드가 하는 일보다 존재 이유와 제약을 설명합니다.
- 외부 계약이나 중요한 제약을 가진 public 타입과 메서드에는 Javadoc을 작성합니다.
- 단순 getter, record 접근자와 의미가 분명한 private 메서드는 생략할 수 있습니다.

### 3.3 Spring Web

- Controller는 요청 변환, 검증 실행과 응답 변환에 집중합니다.
- 비즈니스 규칙은 Controller 밖에서 검증할 수 있게 구성합니다.
- Request DTO에 Bean Validation을 사용합니다.
- JPA Entity를 API 응답으로 직접 반환하지 않습니다.
- HTTP 메서드와 상태 코드는 행위의 의미에 맞게 사용합니다.

### 3.4 JPA와 트랜잭션

- 연관관계는 LAZY를 기본으로 검토합니다.
- 양방향 연관관계와 공개 Setter는 필요한 경우에만 사용합니다.
- 트랜잭션 경계는 유스케이스를 수행하는 계층에 둡니다.
- 조회 전용 트랜잭션은 `readOnly = true`를 검토합니다.
- 외부 API 호출을 DB 트랜잭션 안에서 오래 유지하지 않습니다.
- 목록 조회는 페이징과 N+1 문제를 검토합니다.

### 3.5 패키지

기능 중심 구성을 기본으로 권장합니다.

```text
feature/
  api/
  application/
  domain/
  infrastructure/
```

이 구조와 패키지 이름은 예시입니다. 기능 크기와 현재 코드에 더 단순하거나
명확한 구조가 있으면 담당 엔지니어가 변경할 수 있습니다.

## 4. 엔지니어가 선택하는 사항

다음 내용은 프로젝트 전체 문서에서 미리 정하지 않습니다.

- 기능 개발 순서
- Entity, 테이블과 연관관계 상세 구조
- 새 API의 구체적인 Path와 DTO 설계
- 기능 패키지 이름과 내부 계층 수
- 동시성 제어 구현 방식
- 캐시와 이벤트 도입 여부
- 실시간 통신과 재연결 구현 방식
- 외부 지도 API adapter 구조
- 인증 토큰의 세부 구현과 수명

선택 결과가 제품 동작, 보안 또는 기존 외부 계약에 영향을 주면 `spec.md`에서
확인합니다. 내부 구현 선택이면 `implementation.md`에 근거와 검증 방법을
기록하고 진행합니다.

## 5. Git 협업

- 모든 작업 브랜치는 최신 `main`에서 생성합니다.
- 브랜치 하나는 PR 하나만 담당하고 병합 후 재사용하지 않습니다.
- 이전 작업 브랜치에서 다음 작업 브랜치를 만들지 않습니다.
- 기능 문서, 구현, 테스트, review와 필요한 핸드오프를 같은 PR에 포함합니다.
- 커밋 메시지와 PR 제목은 `[유형] 변경 목적` 형식을 사용합니다.
- 브랜치 이름은 `{유형}/{짧은-kebab-case-목적}` 형식을 사용합니다.

| 유형 | 사용 기준 | 예시 |
|---|---|---|
| `feature` | 사용자 기능 추가 | `[feature] 가입 코드 발급 기능 추가` |
| `fix` | 잘못된 동작 수정 | `[fix] 만료 코드 검증 오류 수정` |
| `refactor` | 동작 변경 없는 구조 개선 | `[refactor] 검증 책임 분리` |
| `chore` | 설정, 빌드와 운영 변경 | `[chore] PR 템플릿 변경` |
| `docs` | 문서만 변경 | `[docs] 병원 수락 정책 보완` |

PR 전 실행 명령과 결과는 기능 `review.md`에 기록합니다. 세부 작업 순서는
저장소 루트의 `AGENTS.md`를 따릅니다.
