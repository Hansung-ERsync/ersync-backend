# 목적지 철회 복구 재알림 요구사항

```text
Feature: destination-withdrawal-recovery-notification
Owner: backend
Related Issue: NONE
Frontend Impact: BOTH
Policy Decision Status: RESOLVED
```

## 목적

- 현재 목적지 병원이 긴급 철회하면 같은 이송 요청에서 새 목적지를 찾습니다.
- 기존 응답 대기 병원은 같은 카드를 유지한 채 최신 정보로 재요청받습니다.
- 기존 수락·거절 이력과 철회 병원 제외 정책을 보존합니다.
- 구급대원이 새 목적지를 직접 선택하기 전까지 자동 목적지를 만들지 않습니다.

## 정책 기준

- 적용 기준은 MVP 요구사항 10장, 13~15장과 기능 15·16의 확정 계약입니다.
- 현재 목적지의 철회만 긴급 복구 재알림을 발생시킵니다.
- 같은 `TransportRequest`를 유지하고 `ACCEPTANCE_WITHDRAWAL` 검색 회차를 하나 시작합니다.
- 검색 원점은 최신 저장 위치이며, 위치가 없으면 최초 요청 위치를 사용합니다.
- 철회한 병원은 목적지에서 해제하고 이후 후보에서 제외합니다.
- 다른 수락 병원이 남아 있으면 요청은 `ACCEPTED_AVAILABLE`, 없으면 `SEARCHING`이 됩니다.
- 두 경우 모두 현재 목적지는 `null`입니다.
- 다른 `ACCEPTED` 병원은 수락을 유지하며 즉시 목적지로 선택할 수 있습니다.
- 기존 `PENDING` 병원은 같은 `offerId`와 응답 권한을 유지합니다.
- 기존 `PENDING` 카드만 `재요청`으로 갱신하고 병원 조직에 다시 알립니다.
- 재요청된 `PENDING` 병원에는 재요청 시점의 최신 최소 임상정보와 현재 위치 기준 거리·ETA를 제공하고 다시 고정합니다.
- 재요청 이후 추가된 임상정보는 새 목적지로 선택되기 전까지 제공하지 않습니다.
- 다른 `ACCEPTED` 병원에는 재요청하지 않으며 최신 임상정보도 목적지 선택 전에는 복원하지 않습니다.
- `REJECTED`, `ACCEPTANCE_WITHDRAWN`, 취소·완료된 병원에는 재요청과 추가 임상정보를 제공하지 않습니다.
- 기존 접촉 병원에는 새 카드를 만들지 않고, 신규 적격 병원에만 새 제안을 만듭니다.
- 새 병원이 수락해도 구급대원이 선택하기 전에는 목적지가 되지 않습니다.
- 복구 검색이 최대 100km에 도달해도 후보 소진 상태로 바꾸지 않습니다.
- 비목적지 수락 병원의 일반 철회는 이번 재알림 동작을 발생시키지 않습니다.

`offeredAt`은 최초 요청 시각으로 보존합니다. 병원 웹은 별도 `lastRequestedAt`과
`reRequested`로 재요청 여부와 최근 요청 시각을 판단합니다. 최초 요청은
`lastRequestedAt == offeredAt`, `reRequested == false`이며 두 값은 null이 아닙니다.
재요청 뒤 `lastRequestedAt`은 재알림 처리 시각이고 `reRequested == true`입니다.

## 시나리오

| # | 상황 | 기대 결과 |
|---:|---|---|
| 1 | A 목적지, B 수락, C 응답 대기, D 거절 상태에서 A가 긴급 철회 | A 제외, B 수락 유지, C 동일 카드 재요청, D 유지 |
| 2 | A 철회 뒤 최신 위치 주변에서 E가 새로 발견됨 | E에만 새 `PENDING` 제안 생성, C에는 새 카드 미생성 |
| 3 | 재요청받은 C가 수락함 | C는 `ACCEPTED`, 자동 확대 중단, 목적지는 여전히 없음 |
| 4 | 구급대원이 B 또는 C를 선택함 | 선택 병원만 현재 목적지, 다른 활성 병원 정보는 다시 동결 |
| 5 | 동일 철회 명령을 재시도하거나 재알림과 C의 수락이 경합함 | 먼저 확정된 명령을 기준으로 복구 회차·재알림·카드 중복 없이 처리 |

## 외부 동작

| 행위 | 요청·응답 또는 상태 변화 |
|---|---|
| 목적지 수락 철회 | 기존 `POST /api/v1/hospitals/me/offers/{offerId}/withdraw-acceptance` 유지 |
| 구급대원 긴급 알림 | 기존 `HOSPITAL_ACCEPTANCE_WITHDRAWN` SSE 뒤 검색 현황 재조회 |
| 병원 재알림 | 기존 `TRANSPORT_REQUEST_RECEIVED` SSE 뒤 ACTIVE 목록·상세 재조회 |
| 병원 활성 목록 | 기존 항목에 `reRequested`, `lastRequestedAt` 추가 |
| 병원 제안 상세 | `timing`에 `reRequested`, `lastRequestedAt` 추가 |
| 구급대원 탐색 현황 | `currentAttempt.triggerType`으로 최초 탐색과 철회 복구 회차 구분 |
| 목적지 재선정 화면 | 목적지 선택 전까지 `새로운 목적지를 찾고 있습니다` 표시, 별도 수락 병원 없음 상태 미사용 |
| 새 목적지 선택 | 기존 목적지 선택 API 사용, 자동 선택 없음 |

재알림 SSE에는 환자정보와 위치를 포함하지 않습니다. REST 재조회 결과가 권위 상태입니다.

## 권한

| 역할 | 허용 작업 | 접근 범위 |
|---|---|---|
| `HOSPITAL_STAFF` | 자기 병원 제안 조회·응답·수락 철회 | JWT의 자기 병원 조직에 전달된 제안만 |
| `PARAMEDIC` | 철회 알림 확인, 자기 요청의 검색 현황 조회·목적지 선택 | 자신이 생성한 이송 요청만 |
| `SUPER_ADMIN` | 없음 | 환자 임상정보·위치·병원 제안 접근 금지 |

## 완료 조건

- [ ] 목적지 긴급 철회가 같은 이송 요청을 유지하고 목적지를 해제함
- [ ] 다른 수락 병원 유무에 따라 `ACCEPTED_AVAILABLE` 또는 `SEARCHING`으로 전이함
- [ ] 철회 병원은 `ACCEPTANCE_WITHDRAWN`으로 닫히고 이후 후보에서 제외됨
- [ ] 최신 저장 위치를 기준으로 복구 검색 회차가 하나만 생성됨
- [ ] 기존 `ACCEPTED` 병원의 상태와 선택 권한이 유지됨
- [ ] 기존 `PENDING` 병원의 `offerId`와 응답 권한이 유지됨
- [ ] `PENDING` 카드의 재요청 여부와 최근 요청 시각이 재연결 뒤에도 복구됨
- [ ] 재요청된 병원만 최신 최소 임상정보와 최신 복구 원점 기준 직선거리·경로거리·ETA를 조회함
- [ ] `REJECTED`·철회·종료 병원에는 재요청과 추가 정보가 전달되지 않음
- [ ] 신규 적격 병원에만 새 제안이 생성되고 목적지는 자동 선택되지 않음
- [ ] 일반 비목적지 수락 철회는 PENDING 재알림을 만들지 않음
- [ ] 철회가 먼저 확정되면 PENDING 병원은 한 번 재알림된 뒤 수락될 수 있음
- [ ] PENDING 병원 수락이 먼저 확정되면 수락을 유지하고 재알림되지 않음
- [ ] 중복·경합에서 활성 복구 회차, 카드와 재알림 신호가 중복되지 않음
- [ ] 후보 소진·전체 재전송·전화 연결 상태가 다시 도입되지 않음
- [ ] 조직 격리, 임상정보·정확한 위치 접근 제한이 유지됨
- [ ] 백엔드는 복구 회차와 목적지 없음 상태를 반환하고 Flutter 문구 계약을 핸드오프함
- [ ] H2·MySQL·로컬 readiness와 Flutter·React 핸드오프 검증이 통과함

## 기능 내 결정 사항

| 쟁점 | 결정 | 이유·영향 |
|---|---|---|
| 재요청 표시 | `reRequested`, `lastRequestedAt` 추가 | 최초 요청 시각을 보존하면서 카드 복구 가능 |
| 병원 SSE | 기존 `TRANSPORT_REQUEST_RECEIVED` 재사용 | 새 이벤트 타입 없이 REST 재조회 유도 |
| 기존 수락 병원 정보 | 수락 유지, 최신 임상 복원 안 함 | 재요청 대상은 `PENDING`으로 제한 |
