# 자동 병원 탐색 및 병원 응답 요구사항

```text
Feature: automatic-hospital-search-response
Owner: backend
Related Issue: NONE
Frontend Impact: BOTH
Policy Decision Status: RESOLVED
```

> 이송 요청 생성 직후 서버가 조건에 맞는 병원을 자동 탐색해 요청을 전달하고,
> 병원이 수락 또는 거절한 결과를 구급대원에게 제공하는 기능입니다. 후보는
> 직선거리로 판정하고 실제 도로 거리와 ETA는 네이버 지도 API로 계산합니다.

## 목적

- 구급대원이 병원을 직접 고르지 않아도 서버가 거리·수신 상태·활성 상태를 기준으로 후보를 선정합니다.
- 수락이 없으면 정해진 시간과 반경에 따라 새 병원으로 자동 확대합니다.
- 병원은 자기 조직에 전달된 요청만 보고 수락 또는 사유가 있는 거절을 할 수 있습니다.
- 구급대원은 병원별 응답, 후보 부족과 후보 소진 상태를 확인하고 같은 요청을 재전송할 수 있습니다.
- 탐색 회차와 병원 응답은 덮어쓰지 않고 감사 가능한 이력으로 보존합니다.

## 이번 기능 범위

### 포함

- 이송 요청 생성 후 별도 병원 선택 없이 시작되는 최초 자동 탐색
- 병원 활성 상태, 응급실 수신 `ON`, 좌표와 검색 회차 중복 여부에 따른 후보 검증
- 최초 10km부터 최소 3곳을 찾을 때까지의 즉시 확대와 최대 100km 제한
- 수락이 없을 때 60초 간격의 반경 확대와 새 후보에만 요청 전달
- 후보 부족, 전원 거절, 무응답과 후보 소진 처리
- 병원 활성 요청 목록·상세 조회
- 병원의 수락과 필수 사유가 있는 거절
- 첫 수락 시 자동 확대 중단 및 여러 병원의 수락 허용
- 구급대원의 탐색·응답 현황 조회와 후보 소진 후 멱등한 재전송
- 후보 병원의 등록된 응급실 연락처 제공과 시스템 밖 전화 연결 지원
- 양쪽 화면의 실시간 갱신 알림과 재연결 후 권위 상태 재조회
- 탐색·전달·응답·후보 소진·재전송 감사 기록

### 제외

- 수락 병원의 목적지 선택·변경
- 수락 이후 병원의 철회와 목적지 철회 후 재탐색
- 이송 중 임상정보·현재 위치·ETA 갱신
- 이송 취소, 인계 완료 요청과 병원 확인
- 병상·수술실·전문의·장비의 실시간 외부 데이터 연동
- 전화 통화 결과에 따른 요청·응답 상태 자동 변경

## 정책 기준

### 후보 병원 조건

다음 조건을 모두 만족한 병원만 현재 검색 회차의 후보가 됩니다.

- 등록된 병원 조직과 병원 공용 계정이 모두 활성 상태입니다.
- 병원 프로필에 유효한 응급실 좌표가 있습니다.
- 응급실 신규 요청 수신 상태가 `ON`입니다.
- 현재 검색 회차에서 같은 요청을 아직 전달받지 않았습니다.

수신 상태 변경은 새 요청의 후보 자격에만 영향을 줍니다. 요청을 전달받은 뒤
`OFF`로 바뀌어도 해당 요청과 응답 권한은 유지합니다. 계정 또는 조직이
비활성화되면 인증·응답은 허용하지 않습니다.

### 검색 반경과 시간

```text
최초 반경: 10km
최소 후보 수: 3곳
반경 확대 단위: 10km
확대 간격: 60초
최대 반경: 100km
첫 수락 발생 시 자동 확대 중단: true
```

- 후보의 반경 포함 여부는 요청 좌표와 병원 좌표 사이의 직선거리(Haversine)로 판정합니다.
- 경계값은 해당 반경 이하이면 포함하며 거리 계산 결과는 서버에서 동일한 정밀도로 정규화합니다.
- 최초 탐색은 10km부터 시작합니다.
- 후보가 3곳 미만이면 기다리지 않고 20km, 30km 순으로 즉시 확대합니다.
- 3곳 이상을 처음 찾은 반경에서 조건을 만족한 모든 병원에 요청을 전달합니다.
- 100km까지 후보가 3곳 미만이어도 발견한 병원에는 모두 전달하고 후보 부족 상태를 표시합니다.
- 수락이 없으면 현재 반경의 전달 시각부터 60초 후 10km 확대하고 새로 포함된 병원에만 전달합니다.
- 중간 반경에서 모든 병원이 일찍 거절해도 다음 확대는 60초 기준을 유지합니다.
- 같은 검색 회차에서 같은 병원에는 중복 요청을 만들지 않습니다.
- 검색 타이머와 병원 수락이 경합하면 서버에 먼저 확정된 상태를 기준으로 처리합니다. 수락 확정 뒤에는 새 후보를 만들지 않습니다.

### 후보 소진과 재전송

- 최대 100km에 후보가 한 곳도 없으면 즉시 `CANDIDATES_EXHAUSTED`가 됩니다.
- 최대 반경에서 전달받은 병원이 모두 거절하면 60초를 기다리지 않고 후보 소진 처리합니다.
- 최대 반경에 미응답 병원이 있으면 마지막 전달 후 60초까지 기다립니다.
- 마지막 대기시간까지 수락이 없으면 미응답 제안을 `NO_RESPONSE`로 확정하고 요청을 후보 소진 처리합니다.
- 거절과 무응답 결과, 검색 반경, 전달 시각과 검색 회차는 삭제하지 않습니다.
- 구급대원은 후보 소진 상태에서만 같은 이송 요청을 재전송할 수 있습니다.
- 재전송은 새 이송 요청이 아니라 새 검색 회차를 만들고 요청 상태를 `SEARCHING`으로 되돌립니다.
- 이전 회차에서 거절하거나 응답하지 않은 병원도 새 회차의 후보가 될 수 있습니다.
- 재전송 명령은 클라이언트 멱등성 키를 사용하며 같은 재시도는 검색 회차를 중복 생성하지 않습니다.

### 병원 수락과 거절

- 병원은 자기 조직에 전달된 `PENDING` 요청만 수락 또는 거절할 수 있습니다.
- 수락은 현재 수용 가능하다는 응답이며 목적지 확정이 아닙니다.
- 한 병원이 수락해도 이미 요청을 받은 다른 병원의 `PENDING` 제안은 유지되어 추가 수락이 가능합니다.
- 첫 수락 시 이송 요청은 `ACCEPTED_AVAILABLE`이 되고 이후 자동 반경 확대만 중단합니다.
- 거절 사유는 아래 값 중 하나가 필수이고 `OTHER`에는 짧은 상세가 필요합니다.

```text
ER_GENERAL_BED_SHORTAGE
ISOLATION_BED_SHORTAGE
OPERATING_ROOM_SHORTAGE
ICU_SHORTAGE
SPECIALIST_UNAVAILABLE
EQUIPMENT_UNAVAILABLE
OTHER
```

- 같은 제안에 대한 수락과 거절 중 서버에 먼저 확정된 한 응답만 유효합니다.
- 같은 멱등성 키와 같은 응답의 재시도는 최초 결과를 반환하고 이력을 중복 생성하지 않습니다.
- 이미 확정된 제안에 다른 응답을 보내면 기존 결과를 유지하고 충돌 오류를 반환합니다.
- 병원 공용 계정 응답에는 계정, 병원 조직과 서버 시각을 기록하며 직원 개인 이름은 받지 않습니다.

### 병원에 제공하는 정보

병원은 자기 조직에 실제로 전달된 요청에 한해 다음 정보를 봅니다.

- 요청 ID, 제안 ID, 검색 회차, 요청 상태와 제안 상태
- 추정 여부를 포함한 나이와 성별
- 발생 유형, 손상 기전·부위, 주증상·부증상과 발생 시각 상태
- Pre-KTAS 단계 또는 긴급 전송 사유
- 최신 AVPU
- 혈압·맥박·호흡수·체온·산소포화도의 값 또는 상태
- 현재 처치 요약
- 구급대 조직과 회신 연락처
- 환자 평가 프로토콜 버전
- 거리, 자동 ETA, 계산 상태와 계산 시각
- 요청 도착 시각, 경과시간과 마지막 임상 갱신 시각

환자 이름, 주민등록번호, 정확한 생년월일, 환자 연락처, 상세 주소와
구급차의 정확한 좌표는 제공하지 않습니다. 회신 연락처는 `PENDING` 또는
`ACCEPTED` 제안에서만 원문으로 제공하고 `REJECTED`·`NO_RESPONSE` 또는
종료 상태에서는 마스킹합니다.

실제 도로 거리와 ETA는 네이버 Directions 5 API로 계산합니다. API 실패는 요청
전달을 막지 않습니다. 이때 ETA와 지도 기반 거리는 `UNAVAILABLE` 상태와 계산
시각 없이 반환하며, 전달·수락·거절 흐름은 계속됩니다.

### 구급대원에게 제공하는 정보

- 현재 요청 상태, 검색 회차, 현재 반경, 후보 부족 여부와 다음 확대 예정 시각
- 병원별 `PENDING`, `ACCEPTED`, `REJECTED`, `NO_RESPONSE` 상태와 서버 응답 시각
- 거절 병원의 사유와 `OTHER` 상세
- 수락 병원의 병원명, 거리·ETA, 수락 시각과 응급실 연락처
- 후보 소진 사유가 전원 거절인지 무응답 포함인지 구분한 결과
- 후보 소진 뒤 전화할 수 있는 후보 병원명과 등록된 응급실 연락처

전화는 클라이언트의 전화 기능으로 시작하고 백엔드 상태를 변경하지 않습니다.

### 실시간 갱신

- 병원에는 새 요청 도착을, 구급대원에게는 수락·거절·무응답·후보 소진·재전송 시작을 서버 처리 후 3초 이내 전달하는 것을 목표로 합니다.
- 병원 대시보드는 새로고침 없이 새 요청을 받을 수 있어야 합니다.
- 실시간 이벤트는 갱신 신호이며 요청·제안 상태 조회 API의 결과를 최종 기준으로 사용합니다.
- 연결이 끊기면 클라이언트가 재연결하고 활성 목록과 현재 상태를 다시 조회해 누락을 복구합니다.
- 실시간 전송 방식과 트랜잭션 안전한 발행 구조는 `implementation.md`에서 결정합니다.

| 4 | 최대 반경의 모든 병원이 거절하거나 마지막 60초까지 응답하지 않음 | 미응답을 `NO_RESPONSE`로 확정하고 요청을 `CANDIDATES_EXHAUSTED`로 바꾸며 구급대원에게 결과를 알림 |
| 5 | 구급대원이 후보 소진 요청을 같은 멱등성 키로 재전송함 | 같은 요청에 새 검색 회차 하나만 생성되고 이전 거절·무응답 병원도 다시 후보로 검토됨 |

## 외부 동작

| 행위 | 요청·응답 또는 상태 변화 |
|---|---|
| 최초 자동 탐색 | 이송 요청 생성 완료 후 클라이언트의 병원 목록 없이 서버가 검색 회차 1을 만들고 후보 제안을 생성함 |
| 병원 활성 목록 조회 | `HOSPITAL_STAFF`가 자기 병원의 `PENDING`·`ACCEPTED` 요청 카드만 조회함 |
| 병원 요청 상세 조회 | 자기 병원의 제안에 연결된 최소 임상정보·회신 연락처·거리/ETA와 상태를 조회함 |
| 병원 수락 | `PENDING` 제안을 `ACCEPTED`로 바꾸고 첫 수락이면 요청을 `ACCEPTED_AVAILABLE`로 바꾸며 양쪽에 알림 |
| 병원 거절 | 필수 사유를 검증해 `REJECTED`로 바꾸고 구급대원에게 병원별 결과를 알림 |
| 구급대원 현황 조회 | 요청 소유자가 검색 회차·반경·후보 부족·병원별 응답·수락 병원 정보를 조회함 |
| 후보 소진 | 최대 반경 규칙에 따라 요청을 `CANDIDATES_EXHAUSTED`로 바꾸고 남은 제안을 `NO_RESPONSE`로 확정함 |
| 재전송 | 요청 소유자가 멱등성 키를 제출해 같은 요청에 새 검색 회차를 하나 생성함 |
| 전화 연결 정보 조회 | 후보 소진 상태에서 요청 소유자에게 연락 가능한 후보 병원과 응급실 연락처를 제공하며 상태는 바꾸지 않음 |
| 실시간 알림 수신 | 이벤트 수신 뒤 클라이언트가 활성 목록 또는 요청 현황을 다시 조회함 |

## 상태 변화

```text
TransportRequest
SEARCHING
  ├─ 첫 병원 수락 ───────────────> ACCEPTED_AVAILABLE
  └─ 최대 반경 소진 ─────────────> CANDIDATES_EXHAUSTED
                                      └─ 재전송 ─> SEARCHING

HospitalOffer
PENDING
  ├─ 수락 ─> ACCEPTED
  ├─ 거절 ─> REJECTED
  └─ 마지막 응답 창 종료 ─> NO_RESPONSE
```

- 목적지 선택과 수락 철회에 따른 후속 상태는 이번 기능에서 변경하지 않습니다.
- 모든 상태 변화는 서버 시각과 행위자 또는 시스템 작업 주체를 기록합니다.

## 권한

| 역할 | 허용 작업 | 접근 범위 |
|---|---|---|
| `PARAMEDIC` | 자기 요청의 검색·병원 응답 현황 조회, 후보 소진 후 재전송, 병원 전화 연락처 조회 | 인증 계정이 소유하고 자기 `EMS_UNIT`에 속한 요청만 접근 |
| `HOSPITAL_STAFF` | 활성 요청·상세 조회, 자기 병원 제안 수락 또는 거절 | 인증 계정과 연결된 병원 조직에 실제 전달된 제안만 접근 |
| `SUPER_ADMIN` | 이 기능의 임상·위치·연락처·병원 응답 API 사용 불가 | 운영 지표 외 환자 이송 데이터에 접근할 수 없음 |
| 미인증 사용자 | 없음 | 모든 API 접근 불가 |

다른 조직의 요청 또는 제안 존재 여부가 노출되지 않도록 권한 밖 리소스는 찾을
수 없는 응답으로 처리합니다.

### 구현·배포 의존 사항

- Dev 배포 전 네이버 클라우드 Maps 애플리케이션과 Directions 5 서버 자격정보가 필요합니다.
- 서버 자격정보는 환경변수 또는 AWS Secrets Manager에서 주입하고 저장소·로그·프론트 응답에 노출하지 않습니다.
- 네이버 API 응답 모델은 도메인과 분리해 향후 제공자 변경이 가능하게 구현합니다.
- 지도 API 실패 시에도 탐색은 계속하고 ETA는 `UNAVAILABLE`로 처리하는 MVP 규칙은 유지합니다.
- 실시간 전송 기술과 네이버 호출 재시도·제한 방식은 `implementation.md`에 기록합니다.

- `implementation.md` 상세 작성과 개발을 진행할 수 있습니다.
