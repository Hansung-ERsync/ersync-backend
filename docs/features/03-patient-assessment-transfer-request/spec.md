# 환자 평가 및 이송 요청 생성 요구사항

```text
Feature: patient-assessment-transfer-request
Owner: backend
Related Issue: NONE
Frontend Impact: BOTH
Policy Decision Status: RESOLVED
```

> 인증된 구급대원이 구조화된 최초 환자 평가를 제출하고, 가입 시 등록한
> 회신 연락처를 서버가 자동으로 연결해 중복 없는 이송 요청을 생성하는
> 기능입니다. 팀 논의 결과를 반영한 개발 기준이며 실제 개인정보와 환자정보는
> 운영 전 검토가 끝날 때까지 사용하지 않습니다.

## 목적

- 병원과 구급대원이 가입할 때 연락처와 필요한 개인정보 제공 동의를 등록합니다.
- 구급대원이 필수 환자 평가와 현장 위치를 안전하게 제출합니다.
- 서버가 인증된 계정의 역할·조직·연락처와 입력 완전성을 검증해 이송 요청을 생성합니다.
- 최초 평가를 구조화된 불변 기록으로 저장하고 현재 환자 요약을 파생합니다.
- 통신 실패 후 재시도해도 같은 요청이 두 번 생성되지 않게 합니다.
- 공식 프로토콜 확정 전에는 버전이 구분된 개발용 기본 규칙으로 기능 흐름을 검증합니다.

## 이번 기능 범위

### 포함

- 병원·구급대원 가입 시 연락처 및 개인정보 제공 동의 기록
- 서버가 지원하는 환자 평가 프로토콜 버전 조회
- 최초 환자 평가와 출발 위치 검증
- 인증된 구급대원 연락처를 이송 요청 당시 값으로 보관
- 이송 요청과 최초 임상 기록 생성
- 현재 환자 요약 생성
- 멱등성 키를 이용한 중복 생성 방지
- 요청 생성 감사 기록

### 제외

- 병원 후보 자동 탐색과 거리별 요청 전달
- 병원 요청 목록·수락·거절·철회
- 목적지 선택과 변경
- 이송 중 임상·위치·ETA 갱신
- 상황별 추가 평가의 입력·검증
- 공식 의료·법률 검토가 완료된 최종 환자 평가 프로토콜 확정
- 실제 운영 환경의 개인정보 보존기간과 물리적 삭제 작업

## 정책 기준

### 확정된 MVP 기준

- 환자 이름, 주민등록번호, 정확한 생년월일, 환자 연락처와 상세 주소는 수집하지 않습니다.
- 필수 임상 항목은 빈칸 대신 값 또는 `확인 불가`, `측정 불가`, `환자 거부` 등 허용된 상태를 가집니다.
- 최초 평가는 환자·발생 정보, 증상과 발생 시각, Pre-KTAS 또는 긴급 전송 예외, AVPU, 다섯 활력징후와 하나 이상의 처치를 포함합니다.
- 측정·관찰·분류·처치 시각, 앱 입력 시각과 서버 수신 시각을 구분합니다.
- 요청마다 환자 평가 프로토콜 버전을 고정하고 Pre-KTAS 기준 버전을 별도로 기록합니다.
- GPS 좌표 또는 구급대원이 지도에서 확인한 좌표가 필요하며 ETA 실패는 요청 생성을 막지 않습니다.
- 클라이언트가 병원, 구급대원 계정 또는 조직을 임의로 지정하지 않습니다.
- 요청 소유자, 소속 구급대 조직과 역할은 인증된 계정에서 결정합니다.
- 클라이언트 멱등성 키가 필요하며 동일 재시도는 요청·임상 기록·감사 기록을 중복 생성하지 않습니다.
- 임상 기록, 정확한 위치와 연락처를 애플리케이션 로그에 남기지 않습니다.

### 팀 합의 사항

#### 가입 연락처와 동의

- 병원은 가입할 때 응급실 연락처를 등록하는 기존 정책을 유지합니다.
- 구급대원은 개인 계정 가입 시 병원 회신용 개인 또는 업무용 전화번호를 등록합니다.
- 병원과 구급대원 가입 화면에 연락처 수집·제공 동의 UI를 둡니다.
- 서버는 동의 여부뿐 아니라 동의 문구 버전과 동의한 서버 시각을 기록합니다.
- 동의하지 않거나 연락처를 입력하지 않으면 가입을 완료할 수 없습니다.
- 병원 연락처는 구급대원이 병원에 연락할 때 사용하고, 구급대원 연락처는 병원이 현장 구급대원에게 회신할 때 사용합니다.

#### 이송 요청의 회신 연락처

- 이송 요청 생성 API는 `callbackContact`를 요청 본문에서 다시 입력받지 않습니다.
- 서버가 JWT로 인증한 구급대원 계정의 등록 연락처를 조회합니다.
- 등록 연락처를 요청 생성 당시의 `callbackContact` 스냅샷으로 저장합니다.
- 구급대원이 이후 계정 연락처를 변경해도 과거 요청의 스냅샷은 바뀌지 않습니다.
- 연락처는 인증, 역할 또는 조직 판정에 사용하지 않습니다.
- 연락처나 유효한 동의 이력이 없는 계정은 이송 요청을 생성할 수 없습니다.

#### 공개와 보존

- 후속 병원 전송 기능에서 요청을 실제로 받은 병원의 `HOSPITAL_STAFF`만 회신 연락처를 조회할 수 있습니다.
- 요청 대기·수락·현재 목적지 상태에서만 전체 번호를 제공하고, 거절·철회·비목적지 전환·완료·취소 후에는 화면과 API에서 번호를 마스킹합니다.
- 다른 병원과 `SUPER_ADMIN`은 구급대원 연락처를 조회할 수 없습니다.
- DB의 연락처 스냅샷은 이송 요청 이력과 함께 보관하되 정확한 보존기간과 삭제·비식별화 기준은 실제 운영 전에 확정합니다.
- 정책 확정 전 개발·테스트 환경에서는 실제 개인번호 대신 테스트 번호만 사용합니다.
- API 오류, 감사 기록과 애플리케이션 로그에는 연락처 원문을 남기지 않습니다.

#### 개발용 환자 평가 프로토콜

- 최초 개발 버전은 `ERSYNC_MVP_1.0`으로 구분합니다.
- 현재 MVP 요구사항과 팀 설계 원칙에서 일치하는 기본 입력을 검증합니다.
- 운영기관이 승인한 공식 의료 프로토콜이나 공식 Pre-KTAS 기준 버전을 의미하지 않습니다.
- 상황별 추가 평가는 정확한 발동 규칙과 typed 입력 계약이 확정될 때까지 `ERSYNC_MVP_1.0` 생성 API에서 받지 않습니다.
- 공식 규칙이 확정되면 기존 버전을 수정하지 않고 새 버전을 추가합니다.
- 요청은 생성 당시 프로토콜 버전을 완료 시점까지 유지합니다.
- Pre-KTAS 기준 버전은 별도 필드로 저장하고 미확정 개발 값을 공식 버전처럼 표시하지 않습니다.

## `ERSYNC_MVP_1.0` 최초 평가 입력

| 구분 | 필수 내용 |
|---|---|
| 환자 기본 | 나이 상태와 조건부 나이 값, 성별 |
| 발생 정보 | 발생 유형, 비질병일 때 손상 기전과 손상 부위, 주증상, 선택적 부증상 |
| 발생 시각 | 정확·추정·확인 불가 상태와 조건부 시각 |
| Pre-KTAS | 1~5 단계·분류 시각 또는 긴급 전송 예외 사유와 조건부 상세 |
| 의식 | AVPU와 관찰 시각, 평가 불가일 때 사유와 조건부 상세 |
| 활력징후 | 혈압·맥박·호흡수·체온·산소포화도의 값 또는 공식 상태, 측정 시각 |
| 처치 | `처치 없음` 또는 하나 이상의 구조화된 처치 기록과 시행 시각 |
| 요청 정보 | 프로토콜 버전, Pre-KTAS 기준 버전, 출발 좌표·확인 방식, 멱등성 키 |

- 나이 값은 0 이상의 숫자로 검증하며 MVP에 없는 임의의 최대 나이 제한은 두지 않습니다.
- `처치 없음`은 다른 처치와 함께 제출할 수 없습니다.
- `OTHER`, 평가 불가와 측정 불가에서 문서가 명시한 사유·상세는 생략할 수 없습니다.
- 활력징후 단위는 API 계약으로 고정하고 자유 문자열로 받지 않습니다.
- 서버는 임상 시각과 앱 입력 시각을 보존하고 서버 수신 시각을 직접 기록합니다.
- 최초 제출 기록은 수정하지 않으며 이후 정정·재평가는 새 기록으로 추가합니다.

## 시나리오

| # | 상황 | 기대 결과 |
|---:|---|---|
| 1 | 병원 또는 구급대원이 연락처와 필수 동의에 체크하고 가입함 | 연락처와 동의 문구 버전·동의 시각이 해당 계정 범위에 저장됨 |
| 2 | 인증된 구급대원이 완전한 기본 평가, 위치와 새 멱등성 키를 제출함 | 등록된 구급대원 연락처가 자동 연결되고 소유 계정·조직·프로토콜 버전이 고정된 요청 하나가 생성됨 |
| 3 | 혈압을 측정하지 못해 `MEASUREMENT_UNAVAILABLE`과 허용된 사유를 제출함 | 빈칸이 아니라 명시적 상태가 포함된 활력징후 기록으로 저장됨 |
| 4 | CPR 진행 중이라 Pre-KTAS를 마치지 못하고 긴급 전송 사유를 제출함 | 단계 없이 `EMERGENCY_UNFINISHED` 상태로 생성되고 이후 완료 평가가 필요한 상태가 유지됨 |
| 5 | 통신 실패 후 같은 계정이 같은 멱등성 키와 같은 내용으로 다시 제출함 | 새 요청·임상 기록·감사 기록을 만들지 않고 최초 생성 결과를 반환함 |

## 외부 동작

| 행위 | 요청·응답 또는 상태 변화 |
|---|---|
| 병원 가입 | 기존 응급실 연락처와 함께 필수 연락처 제공 동의를 제출하고 서버가 동의 이력을 기록함 |
| 구급대원 가입 | 가입 코드·로그인 정보와 병원 회신용 연락처·필수 동의를 제출하고 개인 계정에 등록함 |
| 지원 프로토콜 확인 | Flutter 앱이 서버가 지원하는 환자 평가 버전과 개발·운영 구분을 조회함 |
| 이송 요청 생성 | `PARAMEDIC`이 최초 평가, 출발 좌표와 멱등성 키를 제출하고 공개 요청 ID·상태·프로토콜 버전·서버 생성 시각을 받음 |
| 연락처 연결 | 서버가 인증 계정의 연락처를 요청 스냅샷으로 저장하며 생성 요청·응답에 연락처 재입력을 요구하지 않음 |
| 동일 요청 재시도 | 같은 계정과 멱등성 키의 동일 요청은 기존 결과를 반환함 |
| 충돌 재시도 | 같은 계정과 멱등성 키에 다른 내용을 제출하면 기존 요청을 변경하지 않고 충돌 오류를 반환함 |
| 현재 요약 생성 | 환자 기본·발생·증상, 현재 Pre-KTAS·AVPU·활력징후·처치와 프로토콜 버전을 가리키는 요약을 파생함 |

### 생성 후 상태

- 생성된 요청은 후속 병원 자동 탐색이 시작할 수 있는 `SEARCHING` 상태입니다.
- 서버 저장 성공을 아직 구현되지 않은 병원 전달 성공으로 표시하지 않습니다.
- 지도 제공자의 ETA 계산 실패 여부와 관계없이 임상 요청 원본은 생성됩니다.

## 기존 가입 API 호환성

- 병원 가입에는 기존 `contact`를 유지하고 필수 동의 정보가 추가됩니다.
- 구급대원 가입에는 연락처와 필수 동의 정보가 추가됩니다.
- 기존 요청 본문으로 가입하면 검증 오류가 발생하므로 Flutter와 React 가입 화면을 같은 배포 주기에 갱신해야 합니다.
- 구현과 로컬 검증 후 실제 API 계약과 전환 방법을 양쪽 프론트 핸드오프에 기록합니다.

## 권한

| 역할 | 허용 작업 | 접근 범위 |
|---|---|---|
| 미인증 사용자 | 가입 코드로 연락처·동의를 포함한 회원가입 | 제출한 가입 정보의 검증 결과만 확인 |
| `PARAMEDIC` | 지원 프로토콜 조회, 최초 평가 제출과 이송 요청 생성 | 서버가 인증한 자신의 계정과 소속 `EMS_UNIT`으로 생성하는 요청만 접근 |
| `HOSPITAL_STAFF` | 이 기능의 생성 API 사용 불가 | 후속 병원 전송 기능에서 자기 병원에 전달된 요청만 접근 |
| `SUPER_ADMIN` | 환자정보가 없는 시스템 상태 확인 외 없음 | 임상정보·위치·회신 연락처·이송 요청 결과에 접근할 수 없음 |

## 오류

| 조건 | 기대 결과 또는 오류 코드 | HTTP |
|---|---|---:|
| 가입 연락처·동의 또는 임상 필수 필드 형식이 올바르지 않음 | `COMMON_001` | 400 |
| 인증정보가 없음 | `AUTH_001` | 401 |
| 구급대원이 아닌 역할이 요청을 생성함 | `AUTH_003` | 403 |
| 인증 계정의 조직 유형이 `EMS_UNIT`이 아님 | `COMMON_004` | 403 |
| 가입 연락처 또는 유효한 동의 이력이 없어 요청 컨텍스트를 만들 수 없음 | `USER_005` | 409 |
| 지원하지 않거나 비활성화된 환자 평가 프로토콜 버전 | `PROTOCOL_001` 또는 `PROTOCOL_002` | 404 또는 409 |
| 같은 멱등성 키로 다른 요청 내용을 제출함 | `COMMON_005` | 409 |
