# 목적지 선택·변경 및 수락 철회 요구사항

```text
Feature: destination-selection-change-acceptance-withdrawal
Owner: backend
Related Issue: NONE
Frontend Impact: BOTH
Policy Decision Status: RESOLVED
```

> 구급대원이 수락한 병원 중 한 곳을 현재 목적지로 선택하거나 다른 수락
> 병원으로 변경하고, 수용이 불가능해진 병원은 사유와 함께 수락을 철회하는
> 기능입니다. 현재 목적지는 항상 0곳 또는 1곳이며 모든 변경 이력을 보존합니다.

## 목적

- 구급대원이 여러 수락 병원을 비교한 뒤 실제 이송 목적지 한 곳을 확정합니다.
- 이송 중에도 아직 철회되지 않은 다른 수락 병원으로 목적지를 안전하게 변경합니다.
- 병원은 수락 후 수용이 불가능해지면 필수 사유와 함께 철회합니다.
- 현재 목적지 병원이 철회하면 목적지를 즉시 해제하고 같은 이송 요청으로 병원 탐색을 이어갑니다.
- 선택·변경·철회가 동시에 요청되더라도 목적지와 병원 응답 상태가 모순되지 않게 합니다.

## 이번 기능 범위

### 포함

- 구급대원의 수락 병원 목록과 현재 목적지 조회
- 수락 병원 최초 목적지 선택
- 아직 수락 상태인 다른 병원으로 목적지 변경
- 현재 목적지를 항상 최대 한 곳으로 유지하는 원자적 상태 변경
- 선택되지 않은 수락 병원의 병원 활성 목록·상세 숨김과 이력 보존
- 병원의 필수 사유가 있는 수락 철회
- 선택되지 않아 숨겨진 수락 병원의 최소 응답 이력과 철회 경로
- 현재 목적지 철회 시 목적지 해제, 구급대원 긴급 갱신 신호와 재탐색 시작
- 선택·변경·철회 명령의 멱등성, 동시성 제어와 감사 이력
- Flutter 구급대원 앱과 React 병원 웹을 위한 SSE 갱신 신호 및 REST 재조회 계약

### 제외

- 구급대원의 이송 취소
- 이송 중 임상 평가·처치 추가
- 구급차 최신 위치 업로드, 위치 노후 상태와 이동 중 ETA 재계산
- 인계 완료 요청과 병원 인계 확인
- 전화 통화 결과에 따른 목적지·수락 상태 자동 변경
- 목적지·철회 외 병원 응답 이력 검색·관리 기능

## 정책 기준

### 수락 병원과 현재 목적지

- 수락은 병원이 현재 환자를 받을 수 있다는 의사이며 목적지를 자동 확정하지 않습니다.
- 여러 병원이 동시에 `ACCEPTED`일 수 있습니다.
- 현재 목적지는 없거나 하나뿐이며, 수락 상태인 병원 제안만 목적지가 될 수 있습니다.
- 구급대원은 자기 계정으로 생성한 이송 요청의 목적지만 선택·변경할 수 있습니다.
- 최초 선택은 요청이 `ACCEPTED_AVAILABLE`일 때 허용하고 요청 상태를 `EN_ROUTE`로 변경합니다.
- 목적지 변경은 `EN_ROUTE`에서 허용하며 요청 상태는 `EN_ROUTE`를 유지합니다.
- `HANDOFF_REQUESTED`, `COMPLETED`, `CANCELLED`에서는 목적지를 선택하거나 변경할 수 없습니다.
- 동일 병원이 이미 현재 목적지라면 현재 상태를 반환하고 목적지 이벤트를 중복 생성하지 않습니다.

### 목적지 선택과 변경 효과

- 목적지 선택과 변경은 이송 요청 잠금 안에서 한 트랜잭션으로 처리합니다.
- 새 목적지는 구급대원 앱의 현재 목적지로 표시되고 병원 활성 화면에는 `이동 중` 요청으로 표시됩니다.
- 이전 목적지는 수락 상태와 수락 이력을 유지하지만 현재 목적지에서 해제됩니다.
- 이전 목적지를 포함한 모든 비목적지 수락 병원은 병원 활성 목록과 임상 상세에서 즉시 숨깁니다.
- 비목적지 수락 병원은 구급대원 수락 병원 목록에는 남으며, 철회되지 않았다면 이후 다시 목적지로 선택할 수 있습니다.
- 목적지 선택 전에는 수락 병원의 활성 카드가 유지됩니다.
- 목적지 선택 후에도 아직 응답하지 않은 `PENDING` 제안의 기존 응답 권한은 유지하지만, 이후 임상 갱신과 정확한 위치는 제공하지 않습니다.
- 정확한 현재 위치와 이후 임상 갱신은 현재 목적지 병원만 받을 수 있습니다. 실제 위치·임상 갱신 API는 이번 기능 범위가 아닙니다.
- 새 목적지 병원과 이전 목적지 병원에 각각 최소 실시간 갱신 신호를 보내며, 클라이언트는 REST API로 권위 상태를 다시 조회합니다.

### 병원 수락 철회

- 병원은 자기 조직에 전달되어 수락한 제안만 철회할 수 있습니다.
- 목적지 선택 전에는 해당 병원의 `ACCEPTED` 제안이 활성 제안입니다.
- 목적지 선택 후에는 현재 목적지 병원의 `ACCEPTED` 제안만 활성 목록·임상 상세에 남습니다.
- 선택되지 않아 숨겨진 수락 병원도 최소 응답 이력에서 자기 수락 상태와 시각을 확인하고 철회할 수 있습니다. 환자 임상정보·구급대원 연락처·정확한 위치는 다시 제공하지 않습니다.
- `HANDOFF_REQUESTED` 이후에는 앱에서 철회할 수 없습니다.
- 철회 사유는 다음 중 하나가 필수입니다.

```text
BED_SHORTAGE
OPERATING_ROOM_SHORTAGE
SPECIALIST_UNAVAILABLE
EQUIPMENT_UNAVAILABLE
OTHER
```

- `OTHER`에는 공백이 아닌 짧은 상세 사유가 필요합니다.
- 철회한 제안은 `ACCEPTANCE_WITHDRAWN`으로 변경하고 행위 계정·병원 조직·사유·서버 시각을 이력에 보존합니다.
- 철회한 병원은 다시 `ACCEPTED`로 되돌리지 않습니다.

### 철회 후 목적지와 재탐색

- 현재 목적지 병원이 철회하면 현재 목적지를 같은 트랜잭션에서 해제합니다.
- 구급대원에게 `HOSPITAL_ACCEPTANCE_WITHDRAWN` 갱신 신호를 즉시 보냅니다.
- 철회되지 않은 다른 수락 병원은 목록에 유지되어 구급대원이 바로 선택할 수 있습니다.
- 다른 수락 병원이 남아 있으면 요청 상태는 `ACCEPTED_AVAILABLE`, 남아 있지 않으면 `SEARCHING`으로 변경합니다.
- 같은 `TransportRequest`와 임상·응답 이력을 유지한 채 새 병원 탐색 회차를 시작합니다.
- 재탐색 기준점은 서버가 보유한 가장 최근 구급대원 위치이며, 아직 새 위치가 저장되지 않았다면 요청 생성 좌표를 사용합니다.
- 철회한 병원과 해당 요청에서 이미 연락한 병원에는 철회 재탐색으로 중복 요청을 보내지 않습니다.
- 다른 수락 병원을 목적지로 선택하면 진행 중인 철회 재탐색의 추가 반경 확대를 중단합니다.
- 새 후보가 없어도 기존 수락 병원과 과거 응답 이력은 삭제하지 않습니다.
- 선택되지 않은 비목적지 병원의 철회는 현재 목적지와 `EN_ROUTE` 상태를 유지하고, 불필요한 환자정보 추가 전송을 피하기 위해 재탐색을 시작하지 않습니다.

### 병원 활성 화면과 정보 노출

- 병원 `ACTIVE` 목록은 `PENDING` 제안과, 목적지 선택 전의 `ACCEPTED` 제안 또는 자기 병원이 현재 목적지인 제안만 반환합니다.
- 선택되지 않은 수락 병원은 활성 상세에서 환자 임상정보와 구급대원 연락처를 더 이상 조회할 수 없습니다.
- 이전 수락과 목적지 지정 이력은 DB와 감사 기록에 남습니다. 선택되지 않은 수락 병원에는 자기 수락 상태·시각·철회 가능 여부만 포함한 최소 이력을 제공하고 임상 상세 접근은 허용하지 않습니다.
- `SUPER_ADMIN`, 다른 병원 조직과 다른 구급대원은 목적지·철회 정보에 접근하거나 명령할 수 없습니다.
- SSE 이벤트에는 환자 임상정보, 회신 연락처와 정확한 좌표를 넣지 않습니다.

### 멱등성·동시성·감사

- 목적지 선택·변경과 수락 철회에는 `Idempotency-Key`가 필수입니다.
- 키 형식은 기존 명령과 동일하게 8~100자의 영문·숫자 및 `._:-`만 허용합니다.
- 같은 키와 같은 명령을 재시도하면 최초 결과를 반환하고 목적지·철회·알림·감사 이력을 중복 생성하지 않습니다.
- 같은 키로 다른 명령을 보내면 `COMMON_005`로 거절합니다.
- 서로 다른 목적지 변경이 동시에 들어오면 서버가 먼저 확정한 변경 뒤 다음 명령이 최신 상태를 다시 검증하여 직렬화합니다.
- 같은 제안에 목적지 선택과 수락 철회가 동시에 들어오면 서버에서 먼저 확정된 상태만 유효하고, 나중 명령은 최신 상태와 함께 충돌 오류를 반환합니다.
- 목적지 선택·변경과 수락 철회는 상태 변경, 도메인 이력, 감사 기록과 outbox 저장을 한 트랜잭션에서 처리합니다.

| 2 | A병원으로 이동 중 구급대원이 B병원으로 목적지 변경 | B병원이 원자적으로 현재 목적지가 되고 B 활성 카드가 복구; A 활성 카드는 숨겨지고 두 수락 이력은 유지 |
| 3 | 현재 목적지 A병원이 `SPECIALIST_UNAVAILABLE`로 철회 | A의 철회 이력과 사유를 저장하고 목적지를 해제; 구급대원에게 갱신 신호를 보내며 같은 요청으로 최신 위치 기준 재탐색 |
| 4 | A병원이 현재 목적지인 동안 숨겨진 B병원이 수락을 철회 | B의 최소 응답 이력에 철회가 기록되고 구급대원 목록에서 제외; A는 목적지로 유지되며 재탐색하지 않음 |
| 5 | 목적지 변경과 현재 목적지 철회가 동시에 실행 | 잠금 순서에 따라 한 명령이 먼저 확정되고 나중 명령은 최신 상태를 검증해 모순된 목적지나 철회 상태를 만들지 않음 |
| 6 | 철회 복구 탐색이 소진된 뒤 기존 `PENDING` 병원이 늦게 수락 | 요청을 `CANDIDATES_EXHAUSTED`에서 `ACCEPTED_AVAILABLE`로 복구하고 해당 병원을 목적지로 선택할 수 있음 |
| 7 | 철회 복구 소진 뒤 수동 재탐색을 시작했는데 기존 `PENDING` 병원이 늦게 수락 | 요청을 `ACCEPTED_AVAILABLE`로 복구하고 진행 중인 수동 탐색을 `STOPPED_ON_ACCEPTANCE`로 종료해 새 병원에 불필요한 요청을 보내지 않음 |

## 외부 동작

| 행위 | 요청·응답 또는 상태 변화 |
|---|---|
| 수락 병원·현재 목적지 조회 | 기존 `GET /api/v1/transport-requests/{requestId}/hospital-search`에 현재 목적지와 병원별 목적지 여부를 포함 |
| 목적지 선택·변경 | `POST /api/v1/transport-requests/{requestId}/destination`, `Idempotency-Key`와 수락 `offerId`를 받아 현재·이전 목적지와 요청 상태 반환 |
| 병원 수락 철회 | `POST /api/v1/hospitals/me/offers/{offerId}/withdraw-acceptance`, `Idempotency-Key`와 철회 사유를 받아 제안·요청·목적지 상태 반환 |
| 병원 활성 목록 | 기존 `GET /api/v1/hospitals/me/offers?view=ACTIVE`가 목적지 선택 뒤 비목적지 수락 제안을 제외 |
| 병원 응답 이력 | 기존 `GET /api/v1/hospitals/me/offers?view=HISTORY`가 숨겨진 자기 수락의 최소 상태·시각·철회 가능 여부를 포함 |
| 병원 활성 상세 | 기존 상세 API가 비목적지 수락·철회 제안의 임상 상세 접근을 차단 |
| 실시간 갱신 | 기존 인증 SSE에 `DESTINATION_SELECTED`, `DESTINATION_CHANGED`, `HOSPITAL_ACCEPTANCE_WITHDRAWN` 신호 추가 후 대상별 REST 재조회 |

## 권한

| 역할 | 허용 작업 | 접근 범위 |
|---|---|---|
| `PARAMEDIC` | 수락 병원·현재 목적지 조회, 목적지 선택·변경 | 자신이 생성한 이송 요청만 |
| `HOSPITAL_STAFF` | 수락 철회, 활성 목적지와 최소 응답 이력 조회 | 자기 병원 조직의 `ACCEPTED` 제안만 |
| `SUPER_ADMIN` | 없음 | 환자 임상정보·위치·회신 연락처와 목적지 명령 접근 금지 |

## 오류

| 조건 | 기대 결과 또는 오류 코드 | HTTP |
|---|---|---:|
| 인증 없음·유효하지 않은 Access Token | `AUTH_001` 또는 `AUTH_002` | 401 |
| 역할이 다른 사용자의 명령 | `AUTH_003` 또는 `COMMON_004` | 403 |
| 다른 구급대원의 요청 접근 | 존재 여부를 과다 노출하지 않는 `TRANSPORT_001` | 404 |
| 다른 병원 조직 또는 존재하지 않는 제안 접근 | `TRANSPORT_005` | 404 |
