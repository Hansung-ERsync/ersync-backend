# ERSync 프론트엔드 기능·비기능 요구사항

- 대상: Flutter·React 프론트엔드 개발자와 AI 에이전트
- 상태: MVP 기준안
- 갱신일: 2026-07-25
- 함께 전달할 문서: `context.md`
- 사용 방법: 공통 컨텍스트와 이 문서로 전체 범위를 이해하고, 기능 구현 시 해당 `docs/contracts/*.md`를 추가로 읽는다.

기능 연동 읽기 순서:

```text
공통 컨텍스트
→ 프론트엔드 컨텍스트
→ 해당 기능의 프론트엔드 계약
→ 현재 프론트엔드 코드
```

계약은 백엔드 구현과 테스트를 마친 뒤 작성된다. 실제 dev API 사용은 계약이
`main`에 병합되고 백엔드 배포가 성공한 뒤 시작한다.

## 1. 목적

프론트엔드는 다음 세 사용자 화면을 제공한다.

1. 구급대원용 Flutter 모바일 앱
2. 병원 관계자용 React 웹
3. 슈퍼 관리자용 React 웹

이 문서는 프론트엔드 에이전트가 구현해야 할 프로젝트 기능과 비기능 요구사항만 정의한다. 프론트엔드 코드 컨벤션, 상태관리 방식, 폴더 구조, UI 라이브러리, 오류 코드 처리 방식과 세부 디자인 시스템은 프론트엔드 팀이 별도로 정한다.

## 2. 사용자와 접근 범위

### 2.1 구급대원

- 개인 계정을 사용한다.
- 자신이 생성하거나 담당하는 이송 요청만 볼 수 있다.
- 환자 평가, 병원 요청, 목적지 선택, 이송 중 갱신과 인계 완료 요청을 수행한다.

### 2.2 병원 관계자

- MVP에서는 병원 응급실 공용 계정 하나를 사용한다.
- 자기 병원에 전달된 요청만 볼 수 있다.
- 요청 수락·거절·철회, 이송 상태 확인과 인계 확인을 수행한다.

### 2.3 슈퍼 관리자

- 병원·구급대 조직과 가입 코드를 관리한다.
- 환자 정보와 구급차 위치를 볼 수 없다.

## 3. 공통 계정 기능

### 3.1 로그인

- 구급대원, 병원 관계자와 슈퍼 관리자는 역할에 맞는 화면으로 진입한다.
- 인증이 만료되면 더 이상 보호된 정보를 보여주지 않는다.
- 병원 공용 단말에서는 로그아웃 후 이전 환자 정보가 남지 않아야 한다.

### 3.2 가입 코드 회원가입

1. 사용자가 전달받은 가입 코드를 입력한다.
2. 유효한 코드라면 연결된 조직과 역할을 보여준다.
3. 사용자가 아이디와 비밀번호를 입력한다.
4. 병원 가입이면 응급실 주소와 연락처를 추가로 입력한다.
5. 가입이 완료되면 해당 코드는 다시 사용할 수 없다.

가입 코드가 만료됐거나 폐기됐거나 이미 사용된 경우 가입을 진행할 수 없어야 한다.

## 4. 슈퍼 관리자 웹

### 4.1 조직 관리

- 병원 또는 구급대 조직을 등록한다.
- 조직 이름, 유형과 활성 상태를 확인한다.
- 병원 조직에는 응급실 주소, 위치와 연락처를 등록한다.

### 4.2 가입 코드 관리

- 조직과 가입 대상 역할을 선택한다.
- 유효기간을 3일, 7일 또는 직접 지정한다.
- 코드를 발급하면 원문을 한 번만 확인할 수 있다.
- 발급 이력과 현재 상태를 조회한다.
- 사용 전 코드를 조기 만료할 수 있다.

슈퍼 관리자 화면에는 환자 요청, 병원 응답, 임상 기록과 위치 기능을 제공하지 않는다.

## 5. 구급대원 앱

### 5.1 기본 사용 환경

- 세로 화면과 한 손 조작을 우선한다.
- 현장 이동, 장갑 착용과 불안정한 네트워크를 고려한다.
- 사용자가 입력 단계를 이동해도 작성한 값이 사라지지 않아야 한다.

### 5.2 환자 정보 입력 단계

입력 흐름은 다음 다섯 단계다.

1. 환자·발생 정보
2. 환자 상태 평가
3. 현장 처치
4. 전송 전 확인
5. 이송 중 갱신

새 요청은 적용할 환자 평가 프로토콜 버전을 고정한다. 이송 중에도 같은 버전을 사용한다.

### 5.3 환자·발생 정보

나이:

- 정확한 나이
- 추정 나이
- 확인 불가

성별:

- 남성
- 여성
- 확인 불가

발생 유형:

- 질병
- 비질병
- 기타
- 확인 불가

비질병이면 손상 기전을 추가로 선택한다.

- 교통사고
- 낙상
- 추락
- 둔상
- 관통상
- 화상
- 중독
- 익수·질식
- 폭행·자해
- 기계·농기계 사고
- 기타
- 확인 불가

손상 부위는 복수 선택할 수 있다.

- 머리·얼굴
- 목
- 가슴
- 복부·골반
- 척추
- 상지
- 하지
- 다발성
- 확인 불가

### 5.4 증상과 발생 시각

주증상은 하나를 반드시 선택하고 부증상은 선택 사항이다.

- 의식 저하
- 호흡곤란
- 호흡정지
- 흉통
- 심정지
- 뇌졸중 의심
- 경련·실신
- 외상
- 출혈
- 소화기 증상
- 중독
- 화상
- 임신·분만
- 행동 이상·자해
- 발열·감염
- 기타
- 확인 불가

증상 발생 시각은 정확한 시각, 추정 시각 또는 확인 불가로 기록한다. 필요한 상황에는 마지막 정상 확인 시각, 사고 시각과 심정지 목격 시각을 추가한다.

### 5.5 Pre-KTAS

- Pre-KTAS 1~5 중 하나를 입력한다.
- 단계, 분류 시각과 적용 기준 버전을 함께 관리한다.
- 재평가는 이전 값을 덮어쓰지 않고 새 기록으로 추가한다.
- CPR 진행, 현장 위험 또는 평가 시간 부족 상황에서는 분류 미완료 상태로 긴급 전송할 수 있다.
- 긴급 전송 사유는 필수이며 가능한 즉시 Pre-KTAS를 추가해야 한다.

### 5.6 의식과 활력징후

의식 상태는 AVPU로 기록한다.

- A: 명료
- V: 음성 반응
- P: 통증 반응
- U: 무반응
- 평가 불가

활력징후:

- 혈압
- 맥박
- 호흡수
- 체온
- 산소포화도

각 활력징후에는 숫자 측정값, 측정 불가 또는 환자 거부 중 하나가 있어야 한다. 측정 불가라면 환자 상태, 현장 위험, 손상 부위 영향, 장비 오류 또는 기타 사유를 선택한다.

### 5.7 현장 처치

하나 이상의 항목을 선택한다.

- 처치 없음
- 산소 투여
- 기도 확보
- CPR
- 제세동·AED
- 정맥로·수액
- 약물 투여
- 출혈·상처 처치
- 고정
- 심전도
- 보온·냉각
- 분만 처치
- 기타

`처치 없음`은 다른 처치와 동시에 선택할 수 없다. 처치별 방법, 용량, 부위, 시각과 성공 여부 등 필요한 상세정보를 입력한다. 실패한 처치 시도도 이력에 남긴다.

### 5.8 조건부 추가 평가

증상과 사고 유형에 해당할 때만 다음 입력을 보여준다.

- 동공 반응
- 혈당
- 주요 과거력
- 알레르기
- 복용 약물
- 감염·격리 필요 정보
- 심정지 상세
- 중증 외상 상세
- 흉통·심혈관 의심 상세
- 뇌졸중 의심 상세
- 임신·분만 상세
- 선호 병원과 사전 연락 여부

조건에 따라 열린 필수 항목은 값 또는 확인 불가 상태를 가져야 한다. 선호 병원은 참고 정보이며 자동 병원 탐색과 최종 목적지 선택을 강제하지 않는다.

### 5.9 병원 요청 전송

다음 조건을 모두 만족하면 전송할 수 있다.

- 모든 필수 항목에 값 또는 공식 상태가 있음
- Pre-KTAS 또는 긴급 전송 사유가 있음
- GPS 위치가 있거나 지도에서 현재 위치를 확인함
- 입력한 환자 정보의 임시 저장이 완료됨

ETA 계산 실패는 전송을 막지 않는다. 최초 요청을 받을 병원은 구급대원이 직접 선택하지 않는다.

### 5.10 병원 응답 대기

- 현재 탐색 반경과 요청 중인 병원 수를 확인할 수 있다.
- 병원 수락·거절·무응답 상태가 갱신된다.
- 거절한 병원의 사유를 확인할 수 있다.
- 첫 수락이 발생하면 자동 반경 확대가 중단된 상태를 보여준다.

최대 반경까지 수락한 병원이 없으면 후보 소진 상태를 보여준다.

- 같은 요청을 다시 전송할 수 있다.
- 후보 병원의 응급실 연락처로 전화할 수 있다.
- 전화 결과로 앱의 수락 상태를 자동 변경하지 않는다.

### 5.11 수락 병원과 목적지

수락 병원 카드는 다음 정보를 제공한다.

- 병원명
- 현재 위치 기준 거리
- 자동 ETA
- 수락 시각
- 응급실 연락처
- 병원 위치
- 목적지 선택 동작

여러 병원이 수락할 수 있지만 현재 목적지는 한 곳만 선택한다. 목적지를 변경하면 이전 병원과 새 병원의 상태가 갱신돼야 한다.

### 5.12 이송 중

- 현재 목적지 병원과 위치를 확인한다.
- 활력징후, 의식 상태, Pre-KTAS와 처치를 새 기록으로 추가한다.
- 과거 기록을 덮어쓰지 않는다.
- 최신 값과 시간순 이력을 구분한다.
- 목적지 병원이 수락을 철회하면 즉시 확인할 수 있어야 한다.
- 철회 후에는 같은 이송 건을 유지한 채 재탐색 상태로 전환한다.

### 5.13 이송 취소

인계 완료 요청 전까지 다음 사유로 이송을 취소할 수 있다.

- 환자 이송 거부
- 보호자 자체 이송
- 현장 상황 종료
- 기타

취소된 요청은 재개하지 않는다. 다시 이송하려면 새 요청을 작성한다.

### 5.14 인계 완료

1. 구급대원이 인계 완료를 요청한다.
2. 병원 확인 대기 상태를 보여준다.
3. 목적지 병원이 확인하면 이송을 종료한다.

구급대원 요청만으로 완료 처리하지 않는다.

### 5.15 통신 실패

- 전송되지 않은 입력 내용을 기기에 임시 저장한다.
- 사용자가 동일 내용을 다시 입력하지 않게 한다.
- 전송 성공 여부를 명확하게 구분한다.
- 통신 복구 후 같은 요청으로 다시 전송할 수 있다.

## 6. 병원 웹

### 6.1 요청 대시보드

- 신규 요청을 새로고침 없이 표시한다.
- Pre-KTAS와 요청 경과시간을 기준으로 우선순위를 확인할 수 있다.
- 요청 한 건을 넓은 카드 형태로 표시한다.
- 응급실 수신 상태가 OFF여도 기존 수락·이송 요청은 계속 보여준다.

요청 카드:

- Pre-KTAS 단계
- 추정 여부를 포함한 나이와 성별
- 주증상
- AVPU
- 혈압, 맥박, 호흡수, 체온과 산소포화도
- 처치 요약
- 거리와 ETA
- 요청 도착 시각과 경과시간
- 마지막 임상 갱신 시각

환자 이름, 주민등록번호, 정확한 생년월일, 연락처와 상세 주소는 표시하지 않는다.

### 6.2 요청 상세

- 환자 평가와 처치 상세를 시간순으로 확인한다.
- 최초 기록과 이송 중 추가 기록을 구분한다.
- 측정 시각과 마지막 갱신 시각을 확인한다.
- 최신 임상 요약을 우선 보여주되 이전 기록을 삭제하지 않는다.

### 6.3 수락과 거절

- 병원 내부 상황을 확인한 뒤 수락 또는 거절한다.
- 수락만으로 목적지 병원이 되지는 않는다.
- 거절 시 사유를 반드시 선택한다.

거절 사유:

- 응급실 일반 병상 부족
- 격리 병상 부족
- 수술실 부족
- 중환자실 부족
- 전문의 부재
- 장비 사용 불가
- 기타

기타는 설명을 추가한다.

### 6.4 목적지 선택 이후

- 목적지로 선택된 병원에는 이송 중인 활성 요청을 보여준다.
- 수락했지만 선택되지 않은 병원에서는 활성 요청 카드가 사라진다.
- 선택되지 않은 병원의 수락 이력은 유지한다.
- 이후 새 목적지가 되면 이송 중 요청을 다시 보여준다.
- 목적지에서 해제된 병원은 변경 사실을 알 수 있어야 한다.

### 6.5 수락 철회

수락 후 수용이 불가능해지면 사유를 선택해 철회할 수 있다.

- 병상 부족
- 수술실 부족
- 전문의 부재
- 장비 사용 불가
- 기타

인계 완료 요청 이후에는 앱에서 철회할 수 없다.

### 6.6 구급차 위치와 ETA

- 정확한 현재 위치는 현재 목적지 병원에만 표시한다.
- 약 10초 간격의 최신 위치를 지도에 반영한다.
- 전체 이동 경로는 제공하지 않는다.
- ETA가 계산되지 않아도 환자 요청은 유지한다.
- 위치 수신이 30초 이상 중단되면 마지막 위치와 마지막 수신 경과시간을 표시한다.
- 위치 수신이 재개되면 최신 상태로 자동 복귀한다.
- 위치 미수신만으로 긴급 경고음을 발생시키지 않는다.

### 6.7 인계 확인

- 구급대원이 인계 완료를 요청하면 병원 화면에 확인 요청을 표시한다.
- 현재 목적지 병원만 인계를 확인할 수 있다.
- 병원 확인 후 모든 활성 화면에서 해당 요청을 종료한다.

### 6.8 응급실 수신 ON/OFF

- ON이면 새 요청 후보에 포함된다.
- OFF이면 새 요청을 받지 않는다.
- OFF로 변경해도 이미 수락했거나 이송 중인 요청은 유지한다.
- OFF 전환은 수락 철회로 처리하지 않는다.

## 7. 정보 전달 범위

목적지 선택 전:

- 응답 대기 중인 병원과 수락한 병원에 수용 판단에 필요한 최신 임상 요약을 전달한다.

목적지 선택 후:

- 현재 목적지 병원에만 이후 임상 갱신과 정확한 위치를 전달한다.
- 선택되지 않은 수락 병원에는 이후 임상정보와 정확한 위치를 전달하지 않는다.

완료 또는 취소 후:

- 모든 사용자 화면에서 활성 요청을 제거한다.
- 이력은 즉시 삭제하지 않는다.

## 8. 비기능 요구사항

### 8.1 사용성

- 구급대원 앱은 한 손 조작과 장갑 사용을 고려한다.
- 주요 동작과 숫자 입력은 충분히 큰 조작 영역을 제공한다.
- 필수 항목을 빈칸으로 넘기지 않고 값 또는 공식 상태를 선택하게 한다.
- 중요 동작의 처리 중, 성공과 실패 여부를 구분할 수 있어야 한다.
- 병원 화면은 넓은 화면에서 여러 요청의 우선순위를 빠르게 비교할 수 있어야 한다.

### 8.2 접근성

- Pre-KTAS와 상태를 색상만으로 구분하지 않는다.
- 숫자에는 단위와 측정 상태를 함께 표시한다.
- 글자 확대 시 내용과 주요 동작이 잘리지 않아야 한다.
- 웹은 키보드만으로 주요 기능을 사용할 수 있어야 한다.
- 소리와 진동은 시각적 상태를 보조하는 용도로만 사용한다.

### 8.3 신뢰성과 실시간 갱신

- 신규 병원 요청과 상태 변경을 새로고침 없이 반영한다.
- 실시간 연결이 끊기면 복구 후 최신 상태를 다시 불러온다.
- 중복 동작으로 요청, 수락, 취소와 인계가 여러 번 생성되지 않아야 한다.
- 오래된 화면 상태가 더 최신인 서버 상태를 덮어쓰지 않아야 한다.
- 사용자가 전송 결과를 알 수 없는 경우 성공으로 표시하지 않는다.

### 8.4 성능 목표

- 일반 화면 요청은 정상 부하에서 p95 1초 이내 응답을 목표로 한다.
- 병원 요청과 응답 상태는 서버 처리 후 3초 이내 화면 반영을 목표로 한다.
- 위치는 약 10초 주기로 갱신한다.
- 수치는 부하 테스트와 현장 시험 후 조정할 수 있다.

### 8.5 보안과 개인정보

- 모든 통신은 TLS를 사용한다.
- 역할과 조직 권한이 없는 정보를 화면에 표시하거나 캐시하지 않는다.
- 슈퍼 관리자에게 환자정보와 위치를 제공하지 않는다.
- 환자정보를 URL, 분석 이벤트, 콘솔 로그와 오류 수집 정보에 포함하지 않는다.
- 모바일 임시 저장 데이터는 암호화한다.
- 병원 공용 브라우저에 환자 화면을 장기간 캐시하지 않는다.
- 정확한 위치는 현재 목적지 병원에서만 보여준다.

### 8.6 시간과 이력

- 임상 발생·측정·처치 시각과 앱 입력 시각을 구분한다.
- 현재값과 과거 이력을 구분해 보여준다.
- 정정과 재평가는 이전 기록을 삭제하지 않는다.
- ETA와 마지막 위치에는 계산 또는 수신 시각을 함께 보여준다.

### 8.7 지원 환경

- 구급대원 앱은 이동 중 세로형 모바일 화면을 우선한다.
- 병원과 관리자 웹은 일반적인 데스크톱 브라우저를 우선한다.
- 네트워크가 불안정한 모바일 환경에서 작성 중인 환자 정보를 보존해야 한다.

## 9. MVP 제외 범위

- 병상·수술실·전문의·장비 실시간 DB 화면
- 상황실 협조 요청
- 의료지도
- 병원 직원 개인별 계정과 프로필
- 환자 이름·주민등록번호·연락처 공유
- 전체 GPS 이동 경로와 경로 재생
- 수동 ETA 입력
- 구급대원의 최초 요청 병원 수동 선택
- 시스템의 자동 최종 목적지 결정
- 환자용 서비스
- 복잡한 계정 복구와 비밀번호 찾기

## 10. 검수 기준

- 세 사용자 역할이 자신의 기능과 정보만 볼 수 있다.
- 구급대원이 다섯 단계 환자 입력을 완료하고 병원 요청을 전송할 수 있다.
- 필수 임상값은 값, 측정 불가, 확인 불가 또는 환자 거부 상태로 남는다.
- 통신 실패 후 작성 내용을 복구하고 같은 요청을 재전송할 수 있다.
- 병원은 요청을 수락·거절·철회하고 필수 사유를 입력할 수 있다.
- 여러 수락 병원 중 한 곳을 목적지로 선택하고 변경할 수 있다.
- 목적지가 아닌 수락 병원에서는 활성 요청이 사라진다.
- 후보 소진 후 같은 요청 재전송과 전화 연결을 사용할 수 있다.
- 이송 취소, 목적지 병원 철회와 인계 완료 흐름이 요구사항대로 동작한다.
- 정확한 위치와 ETA는 현재 목적지 병원에만 표시된다.
- 위치 수신 중단 시 마지막 위치와 경과시간이 유지된다.
- 색상 외 수단으로 중요 상태를 구분할 수 있다.
- 환자 직접 식별정보가 화면, 저장 데이터와 수집 정보에 포함되지 않는다.
