# ERSync 프로젝트 안내

```text
Audience: HUMAN
Read Mode: REQUIRED
Target Length: 1~2 pages
```

## 목적

ERSync는 구급대원이 응급환자 정보를 주변 응급실에 전달하고, 병원 응답을 바탕으로 이송 목적지를 정하도록 돕는 시스템입니다. 의료 판단, 119 지령과 법정 의무기록을 대체하지 않습니다.

## 사용자

| 사용자 | 클라이언트 | 주요 작업 |
|---|---|---|
| 구급대원 | Flutter 앱 | 환자 평가, 병원 요청, 목적지 선택, 인계 |
| 병원 관계자 | React 웹 | 요청 검토, 수락·거절·철회, 인계 확인 |
| 슈퍼 관리자 | React 웹 | 조직과 가입 코드 관리 |

- 구급대원은 개인 계정, 병원은 응급실 공용 계정을 사용합니다.
- 승인된 가입 코드를 받은 사용자만 가입합니다.
- 슈퍼 관리자는 환자정보를 볼 수 없습니다.

## 전체 흐름

```text
환자 정보 입력
→ 주변 응급실 요청
→ 병원 수락·거절
→ 구급대원 목적지 선택
→ 환자 상태·위치 갱신
→ 구급대원 인계 요청
→ 목적지 병원 확인
→ 이송 종료
```

여러 병원이 수락할 수 있지만 현재 목적지는 한 곳입니다.

## MVP

- 프로토콜 기반 환자 평가와 Pre-KTAS
- 거리 기반 병원 탐색과 자동 반경 확대
- 병원 수락·거절·철회와 목적지 변경
- 최신 구급차 위치와 ETA
- 이송 중 임상 갱신과 양측 인계 완료
- 조직·가입 코드 기반 계정 등록

병원 자원 실시간 DB 연동, 자동 최종 배정과 전체 GPS 경로 저장은 제외합니다.

## 개발 환경

| 환경 | DB·설정 | 목적 |
|---|---|---|
| `local` | Docker MySQL | 기능 개발과 수동 확인 |
| `test` | H2 + MySQL Testcontainers | 자동 테스트 |
| EC2 dev | RDS + Secrets Manager | `main` 통합 서버 |

- 로컬 개발자는 RDS에 직접 연결하지 않습니다.
- 기능 브랜치 push와 PR은 EC2 dev 서버를 변경하지 않습니다.

## 기능과 PR

기능 하나는 사용자가 하나의 목적을 달성할 수 있는 흐름입니다. 구현 계층을
기준으로 너무 잘게 나누지 않습니다.

```text
기능 문서 작성
→ AI가 정책 충돌·미확정 사항 식별
→ spec 팀 검토·정책 확정
→ 구현 전 확인·implementation 작성
→ 기능 브랜치 구현
→ 로컬 검사
→ review.md 갱신
→ 프론트 영향이 있으면 계약 작성
→ main 대상 PR
```

- 하나의 PR에서 기능의 API, DB, 권한, 오류, 테스트와 문서를 함께 완료합니다.
- Controller, Service, migration만 각각 구현하는 PR은 만들지 않습니다.
- 큰 기능은 독립적으로 검수·배포 가능한 사용자 흐름을 기준으로 나눕니다.
- 프론트 영향이 있으면 `docs/contracts/`에 기능별 연동 계약을 함께 만듭니다.
- 별도의 수동 API 계약 문서는 만들지 않고 프론트 계약에 API 내용을 포함합니다.

## PR 이후 배포

```text
Backend CI / verify
→ 리뷰 승인 1명
→ squash merge
→ main
→ ECR 이미지 생성
→ EC2 자동 배포
→ readiness 확인
→ 실패 시 이전 이미지 복구
```

`main`은 항상 배포 가능한 상태를 유지합니다. 자동 복구가 발생한 경우 원인을
수정한 새 PR로 다시 배포합니다.
