## 프로젝트

ERSync는 구급대원이 응급환자 정보를 주변 응급실에 전달하고, 병원 응답을
바탕으로 이송 목적지를 정하도록 돕는 시스템입니다. 의료 판단, 119 지령과
법정 의무기록을 대체하지 않습니다.

## 사용자

| 사용자 | 클라이언트 | 주요 작업 |
|---|---|---|
| 구급대원 | Flutter 앱 | 환자 평가, 병원 요청, 목적지 선택, 인계 |
| 병원 관계자 | React 웹 | 요청 검토, 수락·거절·철회, 인계 확인 |
| 슈퍼 관리자 | React 웹 | 조직과 가입 코드 관리 |

- 구급대원은 개인 계정, 병원은 응급실 공용 계정을 사용합니다.
- 승인된 가입 코드를 받은 사용자만 가입합니다.
- 슈퍼 관리자는 환자정보를 볼 수 없습니다.

## 서비스 흐름

```text
환자 정보 입력
→ 주변 응급실 요청
→ 병원 수락·거절
→ 구급대원 목적지 선택
→ 환자 상태·위치 갱신
→ 구급대원 인계 요청
→ 목적지 병원 확인
→ 이송 종료
```

여러 병원이 수락할 수 있지만 현재 목적지는 한 곳입니다.

## MVP 범위

- 프로토콜 기반 환자 평가와 Pre-KTAS
- 거리 기반 병원 탐색과 자동 반경 확대
- 병원 수락·거절·철회와 목적지 변경
- 최신 구급차 위치와 ETA
- 이송 중 임상 갱신과 양측 인계 완료
- 조직·가입 코드 기반 계정 등록

병원 자원 실시간 DB 연동, 자동 최종 배정과 전체 GPS 경로 저장은 제외합니다.

## 개발 환경

| 환경 | DB·설정 | 목적 |
|---|---|---|
| `local` | Docker MySQL | 기능 개발과 수동 확인 |
| `test` | H2 + MySQL Testcontainers | 자동 테스트 |
| EC2 dev | RDS + Secrets Manager | `main` 통합 서버 |

로컬 개발자는 RDS에 직접 연결하지 않습니다.

## 작업 원칙

```text
최신 main 갱신
→ 작업 브랜치 생성
→ 기능 문서·구현·로컬 검증 완료
→ main 대상 PR
→ CI·리뷰 후 squash merge
→ main 다시 갱신
→ 다음 작업 브랜치 생성
```

- 브랜치 하나는 사용자 기능 하나 또는 명확한 변경 하나를 완료합니다.
- 다음 브랜치는 이전 작업 브랜치가 아니라 최신 `main`에서 만듭니다.
- 구현, 로컬 검증, 검수 문서와 필요한 연동 계약을 마친 뒤 PR을 만듭니다.
- Controller, Service, migration처럼 구현 계층별로 PR을 쪼개지 않습니다.
- 프론트 영향이 있으면 실제 구현 기준 계약을 같은 PR에 포함합니다.
- 기능 브랜치와 PR은 배포하지 않으며 `main` 병합만 EC2 배포를 시작합니다.
