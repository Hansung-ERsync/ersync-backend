# ERSync MVP 요구사항

- 문서 대상: 기획자, 개발자, 병원·구급 업무 검토자
- 문서 상태: MVP 기준안
- 갱신일: 2026-08-13
- 기준 관계: 이 문서는 제품 정책과 전체 MVP 범위의 단일 기준이다. 공통 컨텍스트는 이를 AI가 읽기 쉽게 해석하며 이 문서를 덮어쓰지 않는다. 기능별 상세 범위는 `docs/features/*/spec.md`에서 확정한다.

## 1. 문서 목적

ERSync는 응급환자 이송 병원을 빠르게 찾고, 구급대원과 병원의 의사소통을 돕는 시스템이다.

이 문서는 다음 내용을 설명한다.

- 구급대원이 어떤 환자 정보를 입력하는가
- 병원이 어떤 정보로 수용 가능 여부를 판단하는가
- 수락 병원 중 실제 목적지를 어떻게 정하는가
- 이송 중 환자 상태와 현재 위치를 어떻게 공유하는가
- 환자 인계를 어떻게 완료하는가

이 시스템은 의료 판단을 대신하지 않는다. 실제 운영 전에는 소방·응급의료·개인정보·의료법 검토가 필요하다.

## 2. 서비스 목표

1. 구급대원이 현장에서 필수 환자 정보를 빠르게 입력한다.
2. 시스템이 가까운 운영 중 응급실에 요청을 전송한다.
3. 병원은 환자 요약을 보고 수락 또는 거절한다.
4. 구급대원은 수락한 병원 중 한 곳을 목적지로 선택한다.
5. 목적지 병원은 이송 중 환자의 최신 상태와 위치를 확인한다.
6. 병원이 환자 인계를 확인하면 요청을 종료한다.

## 3. MVP 이용자

### 3.1 슈퍼 관리자

- 시스템 운영 주체가 사용하는 계정이다.
- 병원과 구급대 조직을 등록한다.
- 조직별 가입 코드를 발급·조회·조기 만료한다.
- 환자 임상 정보는 열람하지 않는다.

### 3.2 구급대원

- 개인별 계정을 사용한다.
- 환자 상태를 평가하고 이송 요청을 생성한다.
- 병원 응답을 확인하고 목적지를 선택한다.
- 이송 중 환자 상태와 현재 위치를 갱신한다.
- 병원에 환자를 인계한 뒤 완료를 요청한다.

### 3.3 병원 관계자

- 병원 응급실 단위 공용 계정 1개를 사용한다.
- 신규 요청을 보고 수락 또는 거절한다.
- 수락 후 상황이 바뀌면 사유를 입력하고 철회할 수 있다.
- 현재 목적지로 선택된 경우 환자 위치와 최신 상태를 본다.
- 환자를 실제로 인계받은 뒤 인계를 확인한다.

## 4. 확정 운영 원칙

1. 최초 요청에는 병원이 수용 여부를 판단하는 데 필요한 정보만 보낸다.
2. 빈칸은 허용하지 않는다. 값을 모르면 `확인 불가`, 측정하지 못하면 `측정 불가`, 환자가 거부하면 `환자 거부`를 선택한다.
3. 측정·관찰·처치 시각과 앱 입력 시각, 서버 수신 시각을 구분한다.
4. 이송 중 새 평가는 기존 기록을 덮어쓰지 않고 추가한다.
5. 최초 요청과 수락 후 화면에 환자 이름, 주민등록번호, 연락처, 상세 주소를 보내지 않는다.
6. 여러 병원이 수락할 수 있다. 수락은 최종 배정이 아니라 현재 수용 가능 의사다.
7. 구급대원이 수락 병원 중 현재 목적지 한 곳을 선택한다.
8. ETA는 지도 API로 자동 계산한다. ETA 계산 실패는 요청 전송을 막지 않는다.
9. 전체 GPS 이동 경로는 저장하지 않는다. 최신 위치만 유지한다.
10. 구급대원의 완료 요청과 목적지 병원의 확인이 모두 있어야 종료한다.
11. 목적지를 선택해도 다른 수락 병원과 응답 대기 병원의 카드는 유지한다. 해당 병원에는 `다른 병원으로 이동 중`을 표시하고 기존 응답 권한을 유지한다.
12. 구급대원은 인계 완료 요청 전까지 필수 사유를 선택해 이송을 취소할 수 있다. 취소된 요청은 재개하지 않는다.
13. MVP에서는 최소 한 병원이 최종적으로 수락한다고 가정한다. 별도의 무응답·후보 소진 상태, 전체 재전송과 전화 연결은 제공하지 않는다.
14. 목적지 병원은 위치 수신이 중단돼도 마지막 위치와 마지막 수신 경과시간을 확인할 수 있다.
15. 목적지 병원이 긴급 철회하면 같은 이송 요청을 유지한다. 철회 병원만 제외하고 최신 위치에서 새 목적지를 찾는다.

## 5. 전체 이용 시나리오

### 시나리오: 환자 발생부터 인계까지

1. 구급대원이 현장에 도착한다.
2. 앱이 현재 GPS 위치를 가져온다.
3. 구급대원이 환자 기본 정보, 증상, 의식, 활력징후, Pre-KTAS, 처치를 입력한다.
4. 값을 알 수 없는 항목은 정해진 사유를 선택한다.
5. 앱이 입력 완료 여부를 검사한다.
6. 시스템이 가까운 응급실을 찾고 요청을 전송한다.
7. 병원은 넓은 요청 카드에서 환자 요약을 본다.
8. 병원은 수락하거나 사유를 선택해 거절한다.
9. 구급대원은 수락 병원 목록에서 한 곳을 목적지로 선택한다.
10. 목적지 병원은 구급차의 최신 위치, 거리, ETA를 본다.
11. 구급대원은 이송 중 새 활력징후·의식·Pre-KTAS·처치를 추가한다.
12. 목적지 병원은 갱신 알림과 최신 요약을 확인한다.
13. 구급대원이 `인계 완료 요청`을 누른다.
14. 목적지 병원이 `환자 인계 확인`을 누른다.
15. 해당 요청은 모든 활성 목록에서 사라지고 이력으로 남는다.

## 6. 조직 등록과 가입

### 시나리오: 병원 가입 코드를 발급하는 경우

1. 슈퍼 관리자가 관리자 웹에 로그인한다.
2. 조직 유형을 `병원`으로 선택한다.
3. 병원 이름을 등록한다.
4. 코드 유효기간을 3일, 7일 또는 직접 설정한다.
5. 시스템이 일회용 가입 코드를 한 번만 표시한다.
6. 운영 주체가 코드를 오프라인 채널로 병원에 전달한다.
7. 병원은 유효기간 안에 코드를 입력하고 공용 계정을 만든다.
8. 사용된 코드는 다시 사용할 수 없다.

구급대 조직도 같은 방식으로 등록한다. 구급대원은 개인별 계정을 만든다.

가입 코드는 원문을 DB에 저장하지 않는다. 서버에는 해시만 저장한다.

## 7. 병원 정보 등록

병원은 최초 가입 때 다음 정보를 직접 입력한다.

- 병원명 확인
- 응급실 주소
- 지도에서 확인한 위도·경도
- 응급실 연락처
- 공용 계정 아이디와 비밀번호

가입 직후 응급실 수신 상태는 `OFF`다. 병원 관계자가 정보를 확인한 뒤 `ON`으로 바꾼다.

MVP에서는 병상·수술실·전문의·장비 상태를 병원 DB와 자동 연동하지 않는다. 병원은 실제 내부 상황을 확인한 뒤 요청마다 수락 또는 거절한다.

## 8. 환자 정보 입력 구조

입력 화면은 다음 5단계로 구성한다.

1. 환자·발생 정보
2. 환자 상태 평가
3. 현장 처치
4. 전송 전 확인
5. 이송 중 갱신

한 손 조작을 고려한다. 큰 선택 버튼과 숫자 키패드를 사용한다. 조건에 맞지 않는 상세 항목은 숨긴다.

### 프로토콜 버전

- 앱은 운영기관이 승인한 환자 평가 프로토콜 버전을 사용한다.
- 새 이송 건을 만들 때 적용 버전을 고정해 기록한다.
- 이송 중에는 같은 버전으로 평가를 이어간다.
- 공식 Pre-KTAS 기준 버전은 앱 평가 프로토콜 버전과 별도로 기록한다.
- 이전 요청은 당시 버전을 유지한다.
- MVP에서는 슈퍼 관리자가 의료 규칙을 화면에서 직접 편집하지 않는다.
- 프로토콜 변경은 의료 검토, 버전 부여, 앱·서버 배포 절차로 진행한다.
- 앱은 입력을 안내하지만 검증되지 않은 자동 의료 판단을 하지 않는다.

예: `ERSync 환자평가 1.0`이 적용된 요청은 배포 중 1.1이 나와도 이송을 마칠 때까지 1.0 기록을 유지한다.

### 8.1 환자·발생 정보

#### 나이

다음 중 하나가 반드시 필요하다.

- 정확한 나이: 숫자
- 추정 나이: 숫자와 `추정` 표시
- 확인 불가

예: 신분증이 없지만 약 70대로 보이면 `70세, 추정`으로 입력한다.

#### 성별

- 남성
- 여성
- 확인 불가

#### 발생 유형

- 질병
- 비질병
- 기타
- 확인 불가

비질병을 선택하면 손상 기전을 추가로 고른다.

- 교통사고
- 낙상
- 추락
- 둔상
- 관통상
- 화상
- 중독
- 익수·질식
- 폭행·자해
- 기계·농기계 사고
- 기타
- 확인 불가

손상 부위는 복수 선택할 수 있다.

- 머리·얼굴
- 목
- 가슴
- 복부·골반
- 척추
- 상지
- 하지
- 다발성
- 확인 불가

### 8.2 주증상과 발생 시각

주증상은 하나를 반드시 선택한다. 부증상은 선택 사항이다.

- 의식 저하
- 호흡곤란
- 호흡정지
- 흉통
- 심정지
- 뇌졸중 의심
- 경련·실신
- 외상
- 출혈
- 소화기 증상
- 중독
- 화상
- 임신·분만
- 행동 이상·자해
- 발열·감염
- 기타
- 확인 불가

증상 발생 시각은 다음 중 하나로 기록한다.

- 정확한 시각
- 추정 시각
- 확인 불가

상황에 따라 마지막 정상 확인 시각, 사고 시각, 심정지 목격 시각을 추가한다.

### 8.3 Pre-KTAS

Pre-KTAS 1~5 중 하나를 입력한다.

각 기록에는 다음 정보가 남는다.

- 단계
- 분류자
- 분류 시각
- 적용 기준 버전

이송 중 다시 평가하면 새 기록을 추가한다. 이전 단계를 수정하거나 삭제하지 않는다.

#### 긴급 전송 예외

분류를 마칠 수 없는 위급 상황에는 `분류 미완료 상태로 긴급 전송`을 사용할 수 있다.

사유는 필수다.

- CPR 진행 중
- 현장 위험
- 평가 시간 부족
- 기타

긴급 전송 후 가능한 즉시 Pre-KTAS 평가를 추가해야 한다.

### 8.4 의식 상태

AVPU로 기록한다.

- A: 명료
- V: 음성 반응
- P: 통증 반응
- U: 무반응
- 평가 불가

평가 불가라면 `현장 위험`, `환자 접근 불가`, `기타` 중 사유를 고른다. 관찰 시각도 함께 저장한다.

### 8.5 활력징후

다섯 항목 모두 값 또는 상태를 가져야 한다.

- 혈압
- 맥박
- 호흡수
- 체온
- 산소포화도

각 항목은 다음 중 하나다.

- 숫자 측정값
- 측정 불가
- 환자 거부

측정 불가 사유는 다음과 같다.

- 환자 상태
- 현장 위험
- 손상 부위 영향
- 장비 오류
- 기타

측정 시각은 기본으로 현재 시각을 넣되 수정할 수 있다.

### 시나리오: 혈압을 측정하지 못한 경우

1. 환자는 심한 움직임으로 커프 적용이 어렵다.
2. 구급대원은 혈압을 빈칸으로 두지 않는다.
3. `측정 불가`를 선택한다.
4. 사유로 `환자 상태`를 선택한다.
5. 나머지 활력징후를 입력하고 요청을 계속한다.

### 8.6 처치

하나 이상을 선택한다.

- 처치 없음
- 산소 투여
- 기도 확보
- CPR
- 제세동·AED
- 정맥로·수액
- 약물 투여
- 출혈·상처 처치
- 고정
- 심전도
- 보온·냉각
- 분만 처치
- 기타

`처치 없음`은 다른 처치와 함께 선택할 수 없다.

처치별 필요한 상세 정보 예시는 다음과 같다.

| 처치 | 추가 정보 |
|---|---|
| 산소 | 방법, 유량, 시작 시각 |
| 기도 확보 | 방법·기구, 시행 시각, 성공 여부 |
| CPR | 시작 시각, 진행 상태, 자발순환회복 여부 |
| 제세동 | 모니터·제세동 여부, 횟수, 시각 |
| 정맥로·수액 | 성공 여부, 수액 종류, 양, 시각 |
| 약물 | 약물명, 용량, 경로, 시각 |
| 출혈 처치 | 부위, 방법, 지혈대 여부, 시각 |
| 고정 | 부위, 방법 |
| 심전도 | 3유도·12유도, 시각, 소견, 전송 여부 |
| 분만 | 처치 내용, 출생 시각 |
| 기타 | 짧은 내용, 시각 |

실패한 처치 시도도 삭제하지 않는다. 병원 카드에는 현재 판단에 필요한 요약을 우선 표시하고, 상세 화면에서 시간순 기록을 확인한다.

### 8.7 상황별 추가 평가

다음 정보는 모든 환자에게 일괄 요구하지 않는다. 증상·사고 유형·프로토콜 조건에 해당할 때만 화면을 연다.

- 동공 반응
- 혈당
- 주요 과거력
- 알레르기
- 복용 약물
- 감염·격리 필요 정보
- 심정지 상세
- 중증 외상 상세
- 흉통·심혈관 의심 상세
- 뇌졸중 의심 상세
- 임신·분만 상세
- 환자 또는 보호자의 선호 병원과 사전 연락 여부

조건이 충족돼 열린 필수 항목은 값 또는 `확인 불가` 상태를 가져야 한다. 선호 병원은 참고 정보다. 자동 병원 탐색과 구급대원의 최종 목적지 선택을 강제로 바꾸지 않는다.

병원 카드에는 현재 수용 판단에 필요한 요약만 표시한다. 상세 기록은 권한이 있는 화면에서 확인한다.

환자 인계 수령자의 개인 이름·서명 입력은 MVP에서 제외한다. 병원 공용 계정의 인계 확인 시각을 기록한다. 법적으로 필요한 별도 서명은 기존 공식 절차에서 수행한다.

## 9. 최초 전송 조건

`병원 요청 전송` 버튼은 다음 조건을 만족할 때 활성화한다.

- 모든 필수 항목에 값 또는 공식 상태가 있음
- Pre-KTAS가 있거나 긴급 전송 사유가 있음
- GPS 위치가 있거나 지도에서 현재 위치를 직접 확인함
- 환자 정보 로컬 저장이 완료됨

병원 탐색에는 위치 좌표가 필요하다. GPS가 실패하면 구급대원이 지도에서 현재 위치를 확인한다. ETA는 전송 필수 조건이 아니다. 대상 병원은 사용자가 직접 고르지 않고 시스템이 탐색 정책에 따라 자동 선정한다.

### 최초 병원 전송 정보

- 추정 여부를 포함한 나이
- 성별
- 발생 유형, 손상 기전·부위
- 주증상과 부증상
- 증상 발생 시각 상태
- Pre-KTAS 또는 긴급 전송 사유
- 최신 AVPU
- 다섯 활력징후의 값 또는 상태
- 현재 처치 요약
- 구급대 조직과 회신 연락처
- 적용한 환자 평가 프로토콜 버전
- 구급차 현재 위치 기준 거리와 자동 ETA
- 마지막 임상 갱신 시각

시스템은 요청 ID, 구급대원 계정, 소속, 역할, 회신 연락처, 요청 시각, 서버 수신 시각, 병원 요청 전달 시각을 자동 기록한다. MVP에서는 가입 코드로 확인된 `구급대원` 역할을 자격 범위로 사용한다. 별도 자격증 종류·번호가 필요하면 운영기관 검토 후 추가한다.

### 전송하지 않는 정보

- 환자 이름
- 주민등록번호
- 정확한 생년월일
- 환자 연락처
- 상세 거주지 주소
- 수용 판단과 관계없는 자유 서술

MVP에서는 병원이 수락한 뒤에도 위 식별정보를 앱으로 보내지 않는다. 실제 인계는 현장 절차를 따른다.

## 10. 후보 병원 탐색

### 10.1 대상 병원 조건

다음 조건을 모두 만족한 병원만 후보가 된다.

- 시스템에 등록된 응급실
- 위치 정보가 있음
- 계정과 조직이 활성 상태임
- 응급실 수신 상태가 `ON`임
- 해당 요청을 이전에 받지 않음
- 수락 철회 후 재탐색이라면 철회 병원이 아님

### 10.2 거리 정책

- 최초 반경: 10km
- 최소 후보 병원 수: 3곳
- 반경 확대 단위: 10km
- 최대 반경: 100km
- 수락이 없을 때 확대 간격: 60초
- 첫 수락 발생 시: 자동 확대 중단

처음 10km 안에 후보가 3곳 미만이면 즉시 20km, 30km 순으로 확대한다. 3곳 이상을 찾은 첫 반경에서 모든 후보에게 보낸다.

### 시나리오: 30km에서 처음 3곳을 찾은 경우

1. 10km 안에는 병원이 1곳 있다.
2. 20km 안에는 병원이 2곳 있다.
3. 30km 안에는 병원이 4곳 있다.
4. 시스템은 30km를 최초 검색 반경으로 정한다.
5. 조건을 만족한 4곳 모두에 요청을 보낸다.
6. 60초 동안 수락이 없으면 40km로 확대하고 새로 포함된 병원에만 보낸다.

100km 안에 3곳이 없어도 발견한 병원에는 보낸다. 구급대원에게 후보 부족 상태를 알린다.

### 10.3 MVP 탐색 종료 가정

- MVP에서는 탐색 과정에서 최소 한 병원이 최종적으로 수락한다고 가정한다.
- 수락이나 거절을 누르지 않은 병원은 계속 `응답 대기`다.
- `무응답`과 `후보 소진`을 별도 상태로 확정하지 않는다.
- 최대 반경 이후 전체 재전송과 병원 전화 연결은 제공하지 않는다.
- 목적지 병원의 긴급 철회로 시작하는 현재 위치 재검색은 15장의 정책을 따른다.

## 11. 병원 요청 화면

병원 웹은 요청을 한 건씩 넓은 카드로 보여준다. 카드의 우선순위는 Pre-KTAS와 요청 경과시간을 기준으로 한다.

카드에는 다음 정보를 크게 표시한다.

- Pre-KTAS 색상과 단계
- 추정 여부를 포함한 나이, 성별
- 주증상
- AVPU
- 혈압, 맥박, 호흡수, 체온, 산소포화도
- 처치 요약
- 거리와 ETA
- 요청 도착 시각과 경과시간
- 마지막 갱신 시각

예시:

> Pre-KTAS 2 · 추정 70세 남성 · 호흡곤란  
> AVPU V · BP 90/60 · HR 118 · RR 30 · SpO2 88% · T 38.1℃  
> 산소 마스크 10L/min 투여 중 · ETA 12분 · 1분 전 갱신

## 12. 병원의 수락과 거절

### 수락

- 병원은 내부 상황을 확인한 뒤 `수락`을 누른다.
- 여러 병원이 같은 요청을 수락할 수 있다.
- 수락만으로 현재 목적지가 되지는 않는다.

### 거절

거절 사유는 필수다.

- 응급실 일반 병상 부족
- 격리 병상 부족
- 수술실 부족
- 중환자실 부족
- 전문의 부재
- 장비 사용 불가
- 기타

`기타`는 짧은 설명을 입력해야 한다. 구급대원은 병원별 거절 사유를 볼 수 있다.

## 13. 수락 병원과 목적지

수락 병원은 카드 목록으로 표시한다.

- 병원명
- 현재 위치 기준 거리
- 자동 ETA
- 수락 시각
- 응급실 연락처
- 위치 보기
- `이 병원으로 이동` 버튼

### 시나리오: 두 병원이 수락한 경우

1. A병원이 먼저 수락한다.
2. B병원도 수락한다.
3. 두 병원은 구급대원 앱의 수락 병원 목록에 표시된다.
4. 구급대원이 A병원을 목적지로 선택한다.
5. A병원에는 `이동 중` 상태와 활성 요청 카드가 표시된다.
6. B병원에는 `수락 완료 · 다른 병원으로 이동 중`이 표시되고 수락은 유지된다.
7. 아직 응답하지 않은 C병원에는 `다른 병원으로 이동 중 · 응답 가능`이 표시된다.
8. B병원과 C병원에는 이후 임상 갱신과 정확한 위치를 제공하지 않는다.
9. 구급대원이 나중에 B병원을 새 목적지로 선택하면 B병원에는 `이동 중`이 표시된다.
10. A병원에는 목적지 변경 알림과 `다른 병원으로 이동 중`이 표시되며 기존 수락은 유지된다.

현재 목적지는 항상 한 곳이다.

## 14. 이송 중 환자 상태 갱신

구급대원은 고정된 빠른 동작으로 새 기록을 추가한다.

- 활력징후 추가
- 의식 상태 변경
- Pre-KTAS 재평가
- 처치 추가

자동 ETA 변화는 지도 API가 처리한다. 상황실 협조 요청은 MVP에서 제외한다.

### 시나리오: 산소포화도가 악화된 경우

1. 최초 요청 당시 SpO2는 92%였다.
2. 이송 중 86%로 낮아졌다.
3. 구급대원이 `활력징후 추가`를 누른다.
4. 새 다섯 항목과 측정 시각을 입력한다.
5. 이전 92% 기록은 유지된다.
6. 목적지 병원에 `활력징후 갱신` 알림이 간다.
7. 병원 카드의 최신 값은 86%로 바뀌고, 상세 이력에서 두 기록을 모두 볼 수 있다.

목적지를 선택하기 전에는 응답 대기 병원과 수락 병원에 수용 판단에 필요한 최신 임상 요약을 전달한다. 목적지를 선택한 뒤에는 현재 목적지 병원에만 이후 임상정보와 정확한 현재 위치를 전달한다. 비목적지 수락·응답 대기 병원에는 이후 갱신을 보내지 않는다. 다만 목적지 병원의 긴급 철회로 복구하는 동안에는 재요청한 응답 대기 병원에만 재요청 시점의 최신 최소 환자정보와 현재 위치 기준 거리·ETA를 다시 제공하고 그 시점으로 다시 고정한다. 기존 수락 병원은 수락을 유지하지만 새 목적지로 선택되기 전까지 기존 정보 고정 시점을 유지한다. 거절·철회·종료된 병원에는 추가 정보를 보내지 않는다.

병원이 요청을 거절하면 수용 판단 목적이 종료되므로 환자 상세·임상 이력·위치
접근을 즉시 차단한다. 병원 HISTORY에는 공개 요청 식별자, 상태, 거절 사유·상세와
처리 시각만 남기며 환자 임상정보, 연락처, 거리와 ETA는 제공하지 않는다.

## 15. 병원의 수락 철회

수락한 병원은 수용이 불가능해진 경우 철회할 수 있다. 사유는 필수다. 목적지로 선택되기 전에는 일반 수락 철회를 사용하고, 목적지로 이동 중에는 `수용 불가 긴급 고지`로 처리한다.

- 병상 부족
- 수술실 부족
- 전문의 부재
- 장비 사용 불가
- 기타

`기타`는 설명을 입력해야 한다.

구급대원이 실제 인계 후 `인계 완료 요청`을 누른 뒤에는 앱에서 수락을 철회할 수 없다. 이 단계의 예외는 현장 운영 절차로 처리하고 운영 전 별도 정책을 검증한다.

### 시나리오: 현재 목적지 병원이 철회한 경우

1. A병원이 현재 목적지다.
2. A병원이 `전문의 부재`로 `수용 불가 긴급 고지`를 전송한다.
3. 구급대원 앱에 긴급 알림이 표시된다.
4. A병원은 현재 목적지에서 해제된다.
5. A병원은 해당 이송 요청의 후보에서 제외된다.
6. 시스템은 같은 이송 요청을 유지하고 구급대원의 최신 위치를 기준으로 새 검색 회차를 시작한다.
7. 다른 수락 병원은 수락을 유지해 즉시 목적지로 선택할 수 있다.
8. 응답 대기 병원은 기존 카드를 유지한 채 `재요청`으로 갱신하고 다시 알림을 받는다.
9. 거절한 병원에는 다시 요청하지 않는다.
10. 현재 위치에서 새로 발견한 병원에는 새 병원 제안을 전송한다.

병원별 요청 카드는 같은 이송 건에서 하나만 존재한다. 응답 대기 병원에 다시 알릴 때 새 카드를 만들지 않고 기존 카드의 요청 시각, 최소 환자정보와 현재 위치 기준 직선거리·경로거리·ETA를 갱신한다. 기존 수락 병원은 재요청하지 않는다. 새 병원이 수락해도 목적지는 자동으로 바뀌지 않으며 구급대원이 직접 선택한다.

구급대원 화면에는 별도 `수락 병원 없음` 상태를 만들지 않는다. 새 목적지를
선택하기 전까지 `새로운 목적지를 찾고 있습니다`를 표시한다.

## 16. 구급대원 이송 취소

구급대원은 요청 전송 이후부터 `인계 완료 요청`을 누르기 전까지 이송을 취소할 수 있다.

취소 사유는 다음 중 하나를 반드시 선택한다.

- 환자 이송 거부
- 보호자 자체 이송
- 현장 상황 종료
- 기타

취소 효과:

- 요청 상태를 `취소됨`으로 변경한다.
- 응답 대기 중이거나 수락한 모든 병원에 취소 알림을 보낸다.
- 모든 병원의 활성 대시보드에서 해당 요청 카드를 제거한다.
- 현재 목적지가 있으면 목적지를 해제한다.
- 임상 기록, 병원 응답, 목적지 변경과 취소 사유는 이력으로 유지한다.
- 취소된 요청은 재개할 수 없다. 다시 이송해야 하면 새 요청을 생성한다.

### 시나리오: 환자가 이송을 거부한 경우

1. 구급대원이 병원 요청을 전송한 뒤 환자가 이송을 거부한다.
2. 구급대원이 `이송 취소`를 누른다.
3. 취소 사유로 `환자 이송 거부`를 선택하고 확인한다.
4. 요청 상태가 `취소됨`으로 바뀐다.
5. 응답 대기 중이거나 수락한 병원에 취소 알림이 전달된다.
6. 모든 병원 활성 화면에서 요청 카드가 사라진다.
7. 이후 이송이 다시 필요해지면 구급대원은 새 요청을 작성한다.

`인계 완료 요청` 이후에는 앱에서 이송을 취소할 수 없다.

## 17. 현재 위치와 ETA

- 앱은 이송 중 약 10초 간격으로 최신 위치를 전송한다.
- 서버는 요청별 최신 위치만 유지한다.
- 전체 이동 경로는 저장하지 않는다.
- 정확한 현재 위치는 현재 목적지 병원에만 보낸다.
- 거리와 ETA는 지도 API로 계산한다.
- ETA에는 `예상` 표시와 계산 시각을 함께 보여준다.
- 서버가 기본 30초 이상 새 위치를 받지 못하면 마지막 위치를 오래된 위치로 표시한다.
- 목적지 병원 화면에는 마지막 위치를 유지하고 `마지막 수신 N초/분 전` 문구를 표시한다.
- 색상만 사용하지 않고 문구나 상태 아이콘을 함께 표시한다.
- 위치 수신이 재개되면 오래된 위치 표시를 자동으로 해제하고 최신 위치로 갱신한다.
- 위치 미수신은 오류가 아닌 상태다. 경고음이나 긴급 알림을 발생시키지 않는다.

### 시나리오: 지도 API가 실패한 경우

1. 환자 요청 전송은 계속 진행한다.
2. ETA는 `계산 불가`로 표시한다.
3. 마지막으로 성공한 거리·ETA가 있으면 계산 시각과 함께 표시한다.
4. 시스템은 잠시 후 자동 재시도한다.

### 시나리오: 위치 수신이 30초 넘게 중단된 경우

1. 목적지 병원은 구급차의 최신 위치를 지도에서 보고 있다.
2. 서버가 30초 동안 새 위치를 받지 못한다.
3. 지도는 마지막 위치를 그대로 유지한다.
4. 위치 옆에 `마지막 수신 30초 전` 상태가 표시된다.
5. 별도 경고음은 울리지 않는다.
6. 새 위치가 수신되면 상태 표시가 사라지고 지도 위치가 갱신된다.

## 18. 인계 완료

### 시나리오: 정상 인계

1. 구급대원이 환자를 목적지 병원에 인계한다.
2. 구급대원이 `인계 완료 요청`을 누른다.
3. 병원 화면에 확인 요청이 표시된다.
4. 병원 관계자가 환자 인수를 확인한다.
5. 병원이 `환자 인계 확인`을 누른다.
6. 요청 상태가 완료로 바뀐다.
7. 모든 병원의 활성 요청과 구급대원 활성 화면에서 사라진다.
8. 요청·응답·목적지 변경·임상 갱신·완료 이력은 감사 기록으로 남는다.

구급대원 또는 병원 한쪽만 눌러서는 완료되지 않는다.

## 19. 응급실 수신 ON/OFF

- `ON`: 새 요청을 받을 수 있다.
- `OFF`: 새 요청 후보에서 제외된다.
- OFF로 바꿔도 이미 수락했거나 이동 중인 요청은 유지된다.
- OFF 전환은 수락 철회가 아니다.

## 20. 통신 실패와 재시도

### 시나리오: 최초 전송 직전에 통신이 끊긴 경우

1. 앱은 입력한 환자 정보를 기기에 암호화해 임시 저장한다.
2. 사용자가 같은 내용을 다시 입력하지 않도록 한다.
3. 화면에 전송되지 않았음을 명확히 표시한다.
4. 통신이 복구되면 같은 요청 키로 재시도한다.
5. 서버는 중복 요청을 만들지 않는다.
6. 전송 성공 후 임시 데이터는 정책에 따라 제거한다.

## 21. 비기능 요구사항

### 21.1 신뢰성

- 전송 요청은 중복 실행돼도 결과가 하나여야 한다.
- 상태 변경은 데이터 저장과 알림 발행이 분리되지 않아야 한다.
- 실시간 연결이 끊기면 재연결하고 누락 상태를 다시 조회한다.
- 서버 시각을 기준으로 순서를 판정한다.
- 이송 취소와 목적지 긴급 철회 후 재검색은 중복 실행돼도 상태와 검색 회차가 중복 생성되지 않아야 한다.

### 21.2 성능 목표

- 일반 API 응답: 정상 부하에서 p95 1초 이내 목표
- 병원 요청·응답 알림: 서버 처리 후 3초 이내 전달 목표
- 병원 대시보드: 신규 요청을 새로고침 없이 표시
- 위치 갱신: 약 10초 주기, 배터리·네트워크 상태에 따라 조정

수치는 부하 테스트와 현장 시험 후 확정한다.

### 21.3 보안과 개인정보

- 모든 통신은 TLS를 사용한다.
- 역할과 조직 단위 접근 제어를 적용한다.
- 관리자에게 환자 임상 정보 권한을 주지 않는다.
- 비밀번호와 가입 코드는 단방향 해시로 저장한다.
- 모바일 임시 저장 데이터는 암호화한다.
- 로그에 환자 정보, 비밀번호, 가입 코드 원문을 남기지 않는다.
- 정확한 환자 위치는 현재 목적지 병원에만 제공한다.

### 21.4 감사 기록

다음 항목은 서버 시각과 행위자를 포함해 남긴다.

- 요청 생성과 전송 대상
- 목적지 병원 긴급 철회와 현재 위치 재검색 회차
- 병원 수락·거절·철회와 사유
- 목적지 선택·변경
- 구급대원의 이송 취소와 사유
- 임상 평가·처치 추가와 정정
- 최신 위치 수신
- 인계 완료 요청과 확인
- 응급실 ON/OFF 변경
- 가입 코드 발급·사용·만료·폐기

임상 기록은 측정·관찰·처치 시각, 앱 입력 시각, 서버 수신 시각을 구분한다.

### 21.5 사용성·접근성

- 구급대원 앱은 한 손 조작과 장갑 사용을 고려한다.
- 주요 터치 영역은 충분히 크게 만든다.
- 색상만으로 Pre-KTAS와 상태를 구분하지 않는다.
- 숫자·단위·측정 상태를 함께 표시한다.
- 병원 화면은 넓은 카드, 큰 글자, 명확한 경고음을 지원한다.
- 모든 중요 동작에는 처리 중·성공·실패 상태가 있다.
- 오래된 위치는 색상과 함께 마지막 수신 경과시간을 표시한다.

### 21.6 관측 가능성

- API 오류율, 알림 지연, 지도 API 실패율을 측정한다.
- 병원 검색 반경과 후보 수를 추적한다.
- 목적지 병원 긴급 철회와 재검색 횟수를 추적한다.
- 수락까지 걸린 시간과 인계 완료 시간을 추적한다.
- 위치가 30초 이상 갱신되지 않은 상태를 측정한다.
- 개인정보를 제외한 상관관계 ID로 장애를 추적한다.

## 22. 데이터 보존 원칙

- 완료와 취소는 화면에서 활성 요청을 숨기는 것이며 DB 즉시 삭제가 아니다.
- 법정 보존기간은 운영 전 법률 검토로 확정한다.
- 보존기간이 지난 데이터는 삭제 또는 비식별화한다.
- 개발·테스트 환경에는 실제 환자 정보를 사용하지 않는다.

## 25. MVP 완료 기준

- 관리자가 조직과 가입 코드를 관리할 수 있다.
- 구급대원과 병원이 확정된 계정 정책으로 가입·로그인할 수 있다.
- 구급대원이 필수 환자 정보를 공식 상태와 함께 입력할 수 있다.
- 긴급 전송 예외와 이후 Pre-KTAS 추가가 가능하다.
- 탐색 정책에 따라 병원 요청이 자동 전송된다.
- 병원이 수락·거절·철회를 사유와 함께 처리할 수 있다.
- 구급대원이 수락 병원을 선택하고 변경할 수 있다.
- 목적지 선택 뒤에도 비목적지 수락·응답 대기 병원이 상태를 확인하고 허용된 응답을 계속할 수 있다.
- 목적지 병원이 긴급 철회하면 해당 병원을 제외하고 같은 요청으로 현재 위치 재검색을 시작한다.
- 구급대원이 인계 완료 요청 전까지 사유와 함께 이송을 취소할 수 있다.
- 최신 위치와 자동 ETA가 목적지 병원에 표시된다.
- 위치 수신 중단 시 마지막 위치와 수신 경과시간이 표시된다.
- 이송 중 임상 갱신이 이전 기록을 보존하며 전달된다.
- 양측 확인으로 인계가 완료된다.
- 권한·중복 요청·통신 실패·동시성 테스트를 통과한다.
